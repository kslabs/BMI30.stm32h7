Позднее разрешил включить внешнюю антенну на всех пяти приборах и завершить

## Детектор Raspberry

- Детекция выполняется на Raspberry. STM32 не перепрошивался и не изменялся.
- Приборы: M01, S10, S11, S12, S13. Живые проходы: S10, верхняя антенна,
  метка «Казино». На 20 см пользователь оценил работу как стабильную; на
  30 см отмечал пропуски при движении.
- Опрос API показал около 16 кадров/с на канал при `avg_n=24`. В измеренных
  интервалах не обнаружены новые потери последовательности, CRC-ошибки или
  переполнения worker. Эти данные не исключают другие причины пропуска.
- На S10 были включены common-mode и четыре подтверждения. Временно, на
  180 секунд, common-mode отключался только в runtime; затем восстановлен.
  Хеш постоянного config и PID core остались прежними. Пользователь сообщил,
  что пропуски остались, но длинных серий стало меньше. Без точной разметки
  проходов количественное улучшение и отсутствие ложных тревог не доказаны.
- Проба с тремя подтверждениями подготовлена, но НЕ запускалась.
  Рабочая исходная настройка: `common_mode_enabled=true`, `confirm0=4`.
- Player Recorder не использовать для живых испытаний: текущий engine
  при его запуске приостанавливает realtime-детекцию.

Данные находятся в `.tmp/tag-detection-20260930/`: `S10-user-pass-01`,
`S10-user-pass-02`, `S10-30cm-common-mode-off`. Между первыми двумя записями
есть промежуток без наблюдения. Число событий `fire_seq` не равно числу
физических проходов. Опрос API не сохраняет каждое промежуточное решение.

## Кольцо T33

Пять кнопок: вверх, вниз, вправо, влево, центр. Bluetooth MAC:
`FF:24:01:26:A0:4A`. Пользователь выбрал перенос подключения с Windows
непосредственно на S10 (`BMI30-D5EB8F26C`, 192.168.0.114).

10 и status `0xC0110007`; доступны два Consumer Control и перо. Первая
проверка Raw Input запускалась на изолированном рабочем столе — это
некорректная проверка поступления физических нажатий. Повтор на обычном
рабочем столе также дал 0 событий; пользователь не видел реакции Windows.
Перезапуск только неисправного интерфейса `pnputil` не выполнен из-за
`Access is denied` от ОС. Это не отказ автоматической проверки разрешений.

Собственный BLE-канал `5833ff03-9b8b-5191-6142-22a4536ef123` временно
слушался 120 секунд: после двух подтверждённых пользователем нажатий данных

При переносе Windows сообщила `paired_before=false`, `ALREADY_UNPAIRED`.
Позже подтверждено Windows `DISCONNECTED`, `paired=false`.

S10: успешное сопряжение, `Paired/Bonded/Trusted=yes`, сначала Connected.
В журнале ядра появились `T33 Consumer Control` и `T33 Touchscreen`, далее

расстояние 1–1,5 м и постоянное синее мигание. Точное значение индикации

фото/точная инструкция, проверка питания и живое наблюдение соединения.

Артефакты: `T33-calibration-01/02.jsonl`, `T33-vendor-notifications-02.jsonl`,

## Инструменты и незавершённые изменения

- `capture_status.py` — наблюдение API; использован в живых сериях.
- `remote_pass_logger.py` — подготовленный приёмник трёх EV_KEY-команд;
  пять тестов состояния проходов прошли. Для стрелок T33 может быть
  недостаточен: кольцо представляет их как движения touchscreen.
- `windows_ring_input.py` — чтение только выбранного MAC; три теста
  фильтрации источника прошли. Теперь запрещает запуск слушателя на
  `CodexSandboxDesktop`. HID-пакеты ещё не декодированы в физические кнопки.
- `capture_ring_inputs.py` — SSH-приёмник всех evdev-интерфейсов заданного
  MAC, в том числе ABS/REL. Ждёт переподключения, временно захватывает только
  эти интерфейсы. При приостановке остановлен SIGTERM; итог 0 событий.
- `tag_profiles_portal.py.inc` и `patch_profiles.py` — незавершённый локальный
  черновик профилей, НЕ установлен на приборах. До применения нужны проверка
  кода и тесты. Известно: доступные файлы фильтров имеют ключ `file`, а черновик
  ошибочно использует `filename`; нормализация при загрузке может отвергнуть
  весь каталог из-за отсутствующего файла фильтра. Проверить также возврат
  вкладки Detection после POST, полноту сохраняемых настроек и откат при
  ошибке сохранения. Новую release-версию пока не создавали.
