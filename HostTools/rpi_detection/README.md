# Наблюдение за детектором Raspberry Pi

`capture_status.py` читает `/api/status` работающего websplit через уже
настроенные и проверенные SSH-алиасы. Обязательна проверка hostname. Скрипт
не открывает USB, не меняет настройки, не запускает воспроизведение или
штатный Player Recorder и не перезапускает службы.

```powershell
py -3 HostTools/rpi_detection/capture_status.py --boards S10 --seconds 120 --interval 0.1
py -3 HostTools/rpi_detection/capture_status.py --boards M01 S10 S11 S12 S13 --seconds 60 --interval 1
```

Сначала дождаться `observation_started: true`, проверить `detector_active`
и нужный канал. Только затем начинать физические проходы. Сравнивать серии
с одинаковыми типом метки, расстоянием, скоростью и ориентацией. Записывать
число реальных проходов и замеченные пропуски; счётчик событий детектора
сам по себе число проходов не устанавливает.

Артефакты: полный JSONL состояний и отдельный JSON с изменениями счётчиков,
скоростью поступления кадров, событиями и состоянием процесса. Каталог
`--output` должен быть новым, чтобы предыдущие результаты не затереть.

Для `run_m02_tag_capture.py` готовность API обозначается `observation_ready`.
Это ещё не готовность разметки кольцом. `ready=true` и событие
`pass_marking_ready` для серии проходов требуют подключённого проверенного
входа кольца и свежей проверки доставки известных нажатий на этом приборе.
После такой физической проверки флаг `--ring-delivery-verified` сохраняет
утверждение оператора о проверке; он сам её не выполняет. Историческая
калибровка и Bluetooth-сопряжение не заменяют проверку доставки. Без флага
наблюдение и сырые отметки сохраняются с неподтверждённой готовностью разметки.
После разрыва кольца готовность снимается; переподключение её не восстанавливает.

В итоговом `summary.json` отдельно указаны `transport_complete`,
`archive_complete`, `observation_complete` и `pass_marking_complete`.
Закрытый архив может содержать ошибки API/кольца и не быть пригодной серией.
Ошибки, потеря данных, смена профиля/процесса/корня, неуспешный финальный
снимок и незавершившиеся потоки снимают `observer_complete`/`observer_finished`.
Полный архив наблюдения всё равно содержит обработанные снимки API:
`exact_raw_replay=false`. Новый анализатор сравнивает настройки обоих каналов,
режим и оба усреднения; текущий шум и счётчики не считаются сменой профиля.

`analyze_ring_passes.py` читает JSONL и `.jsonl.gz`, сохраняет человеческие
hit/miss независимо от событий программы и даёт долю hit с 95% интервалом
Уилсона. Незавершённые, неразмеченные и лишние отметки в знаменатель не входят.
Поле `human_event_evidence` отдельно показывает наличие программных событий
в окне прохода. Отсутствие события в дискретных снимках означает отсутствие
наблюдаемого доказательства, а не доказанный программный пропуск. Это отчёт
о человеческих оценках и наблюдениях, без эталонного пересчёта детектора.

Для записи `run_passive_raw_capture.py`, содержащей обе антенны, канал
анализа нужно задать явно. Тип метки и расстояние указываются по фактическим
условиям; отсутствие этих сведений остаётся неизвестным:

```powershell
py -3 HostTools/rpi_detection/analyze_ring_passes.py SESSION/capture.jsonl.gz --channel upper --tag Casino --distance-cm 40 --output SESSION/passes-analysis.json
```

Адаптер читает `ready`/`status`/`end` и времена самой Raspberry. Итог
`recording_complete` требует одновременно `summary.capture_complete` и
`summary.ground_truth_complete`. Для доли hit учитываются только уникальные
пары start/end с корректными непересекающимися окнами. Повторные ID, конец
без начала, ошибочные и незавершённые отметки сохраняются в отчёте отдельно.
Статистика событий по-прежнему основана на дискретных статусах; наличие
сырых USB-данных само по себе не означает выполненный точный replay.

Для текущего опыта на S07 предусмотрен `passive_ring_input.py`, подключаемый
к passive raw recorder как дополнительный поток ввода. Он работает только с
`BMI30-C9775FBAE`, serial `abdd2dbc9775fbae`, T33 `FF:24:01:26:A0:4A` и явно
выбранным `/dev/input/eventN`. Модуль не выполняет Bluetooth-поиск/сопряжение,
не меняет детектор и не добавляет HTTP-опрос. Захватываются только проверенные
интерфейсы этого кольца; при выходе захват освобождается.

Сначала запись с `--ring-mode calibrate --ring-device /dev/input/eventN`
сохраняет входы и жесты без отметок проходов. После готовности пользователь
выполняет заранее согласованные девять нажатий: по три центра, вверх и вниз
в известном порядке. Затем запись завершается; пользователь явно подтверждает
фактические число и порядок. Девять принятых жестов без такого подтверждения
не разрешают разметку. Манифест создаётся отдельным вызовом:

```powershell
py -3 HostTools/rpi_detection/passive_ring_input.py --verify-log SESSION/events.jsonl --session-id CALIBRATION_UUID --confirm-physical-sequence up,up,up,down,down,down,center,center,center --confirm-physical-count 9 --output SESSION/t33-verified.json
```

Порядок в команде должен совпадать с подтверждённым физическим порядком;
`CALIBRATION_UUID` берётся из свежей записи. Манифест связывает наблюдаемые
жесты с физическими кнопками, точным прибором/MAC/UUID и хешем доказательств.
Неполная, прерванная, смешанная или неоднозначная серия отклоняется.

Серия проносов использует `--ring-mode mark --ring-device /dev/input/eventN`,
`--ring-calibration SESSION/t33-verified.json` и
`--ring-verification-session CALIBRATION_UUID`. Манифест старше часа
отклоняется; старая проверка S10 не подходит. Центр начинает новый проход,
вверх/вниз отмечают человеческие hit/miss согласно свежей калибровке.
Времена границ берутся из входов S07 с обязательным CLOCK_MONOTONIC.
Повторное начало и остановка оставляют незавершённый проход unlabelled;
лишний результат остаётся ignored_mark. Потеря входов снимает готовность
и не обходится автоматическим переподключением.

Ограничения:

- Опрос API не сохраняет каждое промежуточное решение алгоритма. Число
  снимков с отказом фильтра нельзя выдавать за число пропущенных меток.
- `fire_seq` считает переходы в подтверждённое состояние. Удержание метки,
  дрожание сигнала и повторный захват могут изменить связь с физическими
  проходами. Звук также может оставаться активным между событиями.
- `sound_output` и оптическое условие относятся к моменту чтения состояния,
  а `fire_snapshot.timestamp` — к сохранённому событию. Проверять соседние
  снимки, прежде чем утверждать, что событие не включило звук.
- `worker_lifetime_max_ms` — максимум за жизнь счётчика. Для текущей серии
  отдельно считать изменение `over_100ms`; сбросы счётчиков дают `null`.
- Штатный Player Recorder текущего engine приостанавливает realtime
  детекцию (`_player_realtime_suspended`). Для проверки работающей сигнализации
  его запускать нельзя. Этот наблюдатель его не использует.
- Начальное и конечное состояния задают границы расчёта. События до первого
  снимка и после последнего в результаты не включаются.

## Отметки Bluetooth-пультом

`remote_pass_logger.py` подготовлен для запуска на Raspberry через SSH.
T33 сопряжён с S10. 02.10.2026 подтверждена серия вверх 3 → вниз 3 → центр 3:
получены 9/9 команд без разрывов, пользователь подтвердил порядок.
Калибровка `T33_S10_CALIBRATION_20261002.json` имеет статус `verified`:
центр (`tap`) — начало прохода, вверх (`y-`) — сработало, вниз (`y+`) — пропуск.
Влево/вправо пока не калибровались и не используются для отметок проходов.
Не назначать коды по предположению.

1. После сопряжения найти соответствующий `/dev/input/eventN`. Имя, Bluetooth
   MAC и `uniq` устройства должны совпадать с выбранным пультом.
2. Запустить скрипт с `--inspect --hostname BMI30-D5EB8F26C --device ... --mac ...`
   и нажать выбранные кнопки. Режим выводит коды, проходов не регистрирует.
3. Запустить запись с `--start-code N --hit-code N --miss-code N`, указать
   `--tag`, `--distance-cm`, `--channel upper`, длительность `--seconds`.
   JSONL направить в новый файл. Начинать после сообщения `ready: true`.
4. Перед каждым движением нажимать «начало», после прохода — «сработало»
   или «пропуск». Убирать метку из зоны перед следующим проходом.

Записываются нажатия, время на самой Raspberry, полные снимки детектора
с интервалом 100 мс и пользовательский результат каждого прохода. События
пульта обрабатываются независимо от HTTP-запросов. Удержание кнопки не создаёт
новых проходов. Повторное начало или завершение записи без оценки оставляет
проход без результата, а не превращает его в пропуск.

Выбранный пульт временно захватывается только этим процессом: его кнопки
не меняют громкость через рабочий стол. При выходе захват освобождается.
Скрипт проверяет Bluetooth-адрес устройства и не читает другие клавиатуры.
При потере входных событий запись завершается с ошибкой. Пять локальных
тестов проверяют повтор кнопок, незавершённые проходы и запрет запуска при
неработающем детекторе/включённом Player Recorder.

Пульт задаёт границы прохода и субъективную оценку сигнала. Снимки API остаются
дискретными: они не гарантируют сохранение каждой причины отказа или точного
момента звука. Тип метки, расстояние, ориентацию и настройки фиксировать для
каждой серии; менять их между сериями.

### Кольцо T33, сопряжённое с Windows

`windows_ring_input.py` проверяет уже сопряжённое устройство через Windows Raw
Input. Обязателен MAC конкретного кольца; данные остальных клавиатур и мышей
не извлекаются. `--list` выводит доступные интерфейсы. Для калибровки нужны
`--seconds` и `--output` с новым файлом JSONL. Приёмник должен работать на
обычном рабочем столе Windows: изолированный рабочий стол инструментов
перечисляет устройства, но физические нажатия не получает.

Обычные действия кнопок в Windows этот диагностический приёмник не подавляет.
Один пакет HID ещё не означает одно физическое нажатие: назначение кнопок
возможно только после успешной калибровки. Этот инструмент пока не ведёт
совместную с S10 запись размеченных проходов.

Проверка 30.09.2026: T33 имеет BLE-соединение и доступен для GATT-чтения.
Windows видит два интерфейса Consumer Control и интерфейс пера. Интерфейс
мыши не запускается: код проблемы 10, статус `0xC0110007`. Повторная серия
нажатий на обычном рабочем столе дала 0 сообщений Raw Input; пользователь
также не наблюдал реакции Windows. Это не результат проверки метки и не
доказательство неисправности самого кольца. Причина ещё не установлена.

Дополнительно проверено временное включение уведомлений собственного сервиса
`5833ff01-9b8b-5191-6142-22a4536ef123`, характеристика `5833ff03-...`:
после подтверждённых пользователем нажатий центра и вверх уведомлений не было.
Исходное состояние CCCD (`0`, подписка выключена) успешно восстановлено.
Перезапуск только неисправного интерфейса мыши через `pnputil` не выполнен:
Windows вернула `Access is denied` (хотя код выхода команды был `0`). Драйверы,
сопряжение T33 и настройки S10 на этом этапе не изменялись.

Затем пользователь выбрал прямое подключение к S10. При обращении к Windows
получены `paired_before: false` и `Already unpaired`. На S10 выполнено успешное
сопряжение T33 (`Paired/Bonded/Trusted: yes`); Linux создал HID-устройства
Consumer Control и Touchscreen. После этого связь разорвалась, устройства
ввода исчезли. Короткое нажатие центра не восстановило связь; Windows и S10
не обнаружили обычную рекламу кольца в проверенных интервалах. Последняя
попытка подключения завершилась `le-connection-abort-by-local`. Причина
разрыва не установлена. Пользователь указывает расстояние до S10 1–1,5 м
и мигание синим, способ выключения кольца ему неизвестен.

После паузы задача возобновлена. Долгое нажатие центра восстановило связь с
S10; реальные команды получены как касания и движения сенсорного экрана.
Временная задержка назначения доступа udev при переподключении теперь
обрабатывается в `capture_ring_inputs.py` без изменения прав устройств.
Начальное состояние абсолютных координат сохраняется, поскольку Linux
не повторяет неизменившиеся координаты в каждом событии.

`ring_gestures.py RECORDING.jsonl` разбирает записанные касания в `tap`,
`x+`, `x-`, `y+`, `y-` либо `unknown`. Семь тестов проверяют сохранение
координат, начало записи на уже подключённом устройстве, однократный учёт
жеста и повреждённый поток. Направление жеста ещё нельзя автоматически
считать физическим направлением кнопки.

До выбора внешней антенны зарегистрированы тайм-ауты Bluetooth и потери команд
даже в медленной серии. Сырые HID-отчёты также содержали неполные данные,

событий детектора; три теста проверяют старые снимки, другой канал,
позднее получение события и незавершённые отметки.

Эта серия не содержит непрерывных исходных сигналов АЦП. Инвентаризация
всех 8 992 снимков (`replay-data-inventory.json` рядом с архивом) подтверждает:
сохранены показатели, события и небольшие диагностические фрагменты;
полных массивов кадров обоих каналов нет. Точный повторный расчёт детектора
с изменёнными параметрами по этой записи невозможен. Интервалы вне отметок
прохода также нельзя автоматически считать шумом: отсутствие метки там
не было подтверждено пользователем.

Для подбора воспроизведением требуется полная непрерывная запись обоих
каналов с порядком/временем кадров, настройками, отметками проходов и
отдельными интервалами без метки. Повторный расчёт должен использовать
тот же алгоритм, что и живая детекция, с предварительной проверкой совпадения
при исходных настройках. Текущий Player при записи/загрузке приостанавливает
живую детекцию; его расчёт воспроизведения также отличается от рабочего
пути common-mode/истории кадров, поэтому он не является эталонным пересчётом.

## Внешняя антенна CM5 и проверка при загрузке

На M01, S10, S11, S12, S13 установлен `dtparam=ant2` и включена служба
`bmi30-antenna-check.service`. Она проверяет фактические уровни ANT1/ANT2,
сохраняет `/run/bmi30-antenna-check/status.json` и не останавливает детектор.
Проверка не определяет физическое наличие антенного кабеля.
На M01 настроены обе установки, USB и eMMC; сейчас прибор работает с USB.
Исходники: `antenna_check.py`, `bmi30-antenna-check.service`.
Итог применения и проверок: [EXTERNAL_ANTENNA_FLEET_20260930_RU.md](EXTERNAL_ANTENNA_FLEET_20260930_RU.md).
