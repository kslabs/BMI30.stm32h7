# BMI30: запрос параметров STM32 и план служебного сетевого канала

Статус документа: проект требований и план экспериментальной разработки.

Назначение документа:

1. получить от разработчика STM32 недостающие параметры существующей проводной
   синхронизации и обмена данными;
2. измерить фактическое качество синхронизации, а не оценивать его только по
   скорости интерфейса;
3. проверить, улучшится ли проводная синхронизация, если освободить провод от
   основной передачи данных или дать синхронизации строгий приоритет;
4. разработать служебный канал данных через Ethernet/Wi-Fi с автоматическим и
   безопасным возвратом на провод;
5. подготовить транспорт для будущей совместной обработки нескольких BMI30 как
   антенной системы.

Документ не разрешает отключать проводной канал. Провод физически и логически
остаётся на всех приборах и является обязательным резервным каналом.

## 0. Результат аудита и реализация firmware 1.2.45

Проверка исходного кода уточнила важное исходное предположение: сырые ADC-данные
по RS-485 **не передаются и до этой версии не передавались**. Они идут с локальной
STM32 на Raspberry Pi через USB. В проводном обмене остаются sync, два байта
master-status, выбранный двухбайтный ответ slave, sensor/optic/DetADC, identity и
редкие служебные role-пакеты. Поэтому под «переносом остальных данных» далее
понимается перенос status/identity/sensor/role-состояния между Raspberry Pi по IP,
а не перенос уже отсутствующего на RS-485 сырого ADC-потока.

Подтверждённые по коду параметры текущей реализации:

| Параметр | Значение в firmware 1.2.45 |
|---|---|
| Физический sync | Обычный UART-байт на общей half-duplex RS-485, отдельного capture-фронта нет |
| UART | USART2, 240000 бод, 8N1, без flow control |
| Sync marker | `0x25`/`0xA5`, один байт на завершение DMA-буфера |
| Штатный профиль | 600 семплов × 400 буферов/с = 240000 семплов/с |
| Частота sync-байтов | 400 Гц; двухуровневый marker меняет полярность и имеет 200 Гц |
| ADC trigger | TIM15 TRGO UPDATE, PSC=0, номинальный ARR=1144 при timer clock 275 МГц |
| Фазовый счётчик | TIM5, 32 bit, PSC=0, номинально 275 МГц, около 3,636 нс/тик |
| Приём sync | USART2 RXNE interrupt; метка получается после UART-символа и компенсируется в алгоритме |
| UART symbol | 10 бит, около 41,67 мкс, около 11458 тиков TIM5 |
| ADC sample | около 4,167 мкс, около 1145 тиков TIM5 |

При штатных 400 буферах/с верхняя кодовая оценка RS-485 без редких служебных
кадров: `sync + master status + selected slave status = 5 UART bytes/cycle`, то
есть около 20 кбит/с или 8,33% линии. Строгий `SYNC_ONLY` оставляет
`1 byte/cycle`, около 4 кбит/с или 1,67%. Это не является измеренной осциллографом
загрузкой и не доказывает улучшение jitter.

В firmware 1.2.45 добавлено:

- `WIRE_FULL` (`mode=0`) — прежний обмен и безопасный boot/default;
- `SYNC_PRIORITY` (`mode=1`) — sync имеет отдельный mailbox и абсолютный приоритет,
  sensor events остаются немедленными, обычные slave-status прореживаются 1:4;
- `SYNC_ONLY` (`mode=2`) — на RS-485 остаётся только sync-байт: master-status,
  slave-status, sensor, identity и новые role-передачи не запускаются;
- безопасный вход в `SYNC_ONLY`: уже начатый многобайтовый кадр сначала
  заканчивается, переход отражается отдельным диагностическим флагом;
- lease 250…60000 мс. Истечение lease, `STOP_STREAM`, `HOST_RX_CLEAR`, USB
  disconnect или закрытие Vendor IF немедленно возвращают `WIRE_FULL`;
- отдельный однопозиционный mailbox «последняя sync-граница»: заполненная
  служебная очередь больше не может молча выбросить sync; считаются deferred,
  coalesced и максимальная задержка запуска;
- исправлена атомарность `sync + master_status[2]`: посторонний байт из очереди
  больше не может вклиниться между ними;
- USB-команда `0x45 SET_WIRE_MODE` и EP0 `0x46 GET_SYNC_DIAG` (`SYN1`, 84 байта)
  с `boot_id`, `transport_epoch`, lease, фазой, TIM5 frequency, UART/sync
  счётчиками и причиной последнего fallback;
- Raspberry helper `usb_vendor.USBStream.set_wire_mode()/get_sync_diag()` и
  стендовая утилита `HostTools/vendor_wire_mode.py`.

Lease-продление идемпотентно и не вставляет `STAT`/`EVT1` в USB ADC stream.
Рабочий порядок Raspberry: сначала поднять Ethernet/Wi-Fi mirror, подтвердить
приём и непрерывность кадров, затем включить сокращённый режим с
`transport_epoch`; обновлять lease быстрее его трети; при любой неопределённости
послать `WIRE_FULL`. Перевести нужно каждую локальную STM32 через её собственную
Raspberry Pi. Radio/IP arrival time не является временем измерения.

Ограничение текущего этапа: 32-байтовый USB frame уже несёт `dma_seq` в поле
`reserved`, а `SYN1` — текущий `buffer_count` и `boot_id`, но непрерывного
64-битного `first_sample_counter` и общего `sync_epoch` в каждом ADC-кадре пока
нет. Поэтому когерентную антенную обработку нельзя считать готовой только по
этой доработке. Сначала нужны одинаковые аппаратные измерения FULL/PRIORITY/ONLY,
затем — версия сетевого кадра с `boot_id + sync_epoch + first_sample_counter`.

## 1. Исходные условия

Зафиксированные исходные условия:

- проводная синхронизация и групповой обмен реализованы в STM32;
- проводной канал не удаляется и всегда доступен как основной или резервный;
- Ethernet и Wi-Fi могут быть доступны оба, только один из них либо ни один;
- при отсутствии IP-канала вся необходимая синхронизация и передача данных
  должны продолжать работать по проводу;
- верхняя частота полезного входного сигнала ограничена узкополосным фильтром и
  не превышает приблизительно 6–10 кГц;
- Raspberry Pi получает поток измерений от локального STM32 через USB, поэтому
  IP-каналу не требуется переносить больше данных, чем реально выдаёт USB;
- по предварительной оценке USB-поток при кадре 600 семплов не превышает
  1 Мбайт/с на прибор;
- основной рабочий режим использует 200 семплов по 16 бит, усреднение восьми
  пакетов и итоговую частоту рабочих пакетов не выше приблизительно 50 Гц;
- точное число каналов в расчёте потока, реальная частота ADC, смысл текущего
  timestamp и точное место усреднения должны быть подтверждены отдельно;
- существующий STM32-протокол поддерживает идентификаторы приборов 0…31 и уже
  передаёт на Raspberry Pi групповые статусы;
- сетевой канал должен давать запас для расширенного обмена данными, но время
  прихода IP-пакета не должно использоваться как время измерения.

Главное разделение понятий:

- **синхронизация измерения** — выравнивание ADC/timer/sample counter разных
  STM32;
- **транспорт данных** — доставка уже измеренных семплов и результатов между
  Raspberry Pi;
- **задержка доставки** не равна ошибке синхронизации, если каждый кадр имеет
  точную STM32-метку времени или общий счётчик семплов;
- частота служебных пакетов не равна частоте ADC и сама по себе не определяет
  точность фазового выравнивания.

## 2. Рабочая гипотеза

На первом этапе проверяется следующая архитектура:

```text
STM32 Master ───────── проводная синхронизация ───────── STM32 Slave(s)
    │ USB                                                     │ USB
Raspberry Pi coordinator ───── Ethernet/Wi-Fi data ───── Raspberry Pi node(s)
```

В штатном гибридном режиме:

- провод продолжает передавать синхронизацию, аварийные состояния и минимальный
  обязательный служебный набор;
- объёмные измерения и расширенные статусы передаются через Ethernet или Wi-Fi;
- при отказе IP-транспорта провод автоматически возвращается к полному обмену;
- смена транспорта не сбрасывает STM32 sample counter и не создаёт новую шкалу
  времени;
- принимающая сторона удаляет дубликаты по идентификатору сеанса и счётчику
  семплов.

Предположение о том, что освобождение провода улучшит синхронизацию, требуется
доказать измерением. Улучшение возможно, если синхронизация передаётся пакетами
по той же шине и сейчас задерживается арбитражем, длинными кадрами, повторными
передачами или обработчиками прерываний. Если синхронизация использует отдельный
аппаратный импульс и hardware capture, удаление данных с шины может почти не
изменить точность.

Простое увеличение частоты синхропакетов также не гарантирует улучшения. Ошибка
может определяться разрешением таймера, задержкой ISR, способом коррекции
slave-таймера, дрейфом генераторов или связью ADC trigger с таймером. Сначала
нужно найти основной источник ошибки.

## 3. Какую точность действительно требуется получить

Для синусоидальной составляющей связь временной ошибки и фазовой ошибки:

```text
phase_error_deg = 360 × signal_frequency_hz × time_error_s
time_error_s = phase_error_deg / (360 × signal_frequency_hz)
```

Ориентировочная чувствительность на верхней границе полосы:

| Ошибка времени | Фаза при 6 кГц | Фаза при 10 кГц |
|---:|---:|---:|
| 1 мкс | 2,16° | 3,6° |
| 5 мкс | 10,8° | 18° |
| 10 мкс | 21,6° | 36° |
| 25 мкс | 54° | 90° |

До выбора целевой цифры нужно определить будущий способ совместной обработки:

1. **Объединение событий/score после усреднения.** Допуск может быть существенно
   мягче периода входного сигнала; важнее общий номер рабочего окна.
2. **Выравнивание формы сигнала и взаимная корреляция.** Нужны единая шкала
   семплов и ошибка заметно меньше периода 10 кГц, то есть значительно меньше
   100 мкс.
3. **Когерентная фазовая обработка.** Может потребоваться единицы микросекунд или
   меньше, а также калибровка постоянной задержки каждого тракта.

Рекомендуется утвердить два отдельных критерия:

- `T_event` — допустимое расхождение рабочего пакета/окна для объединения
  результатов детектора;
- `T_sample` — допустимое расхождение одинакового физического семпла между
  STM32 для корреляционной или фазовой обработки.

### 4.4. Возможность режима «проводная синхронизация без объёмных данных»

Нужно подтвердить возможность следующих функций firmware:

1. Раздельно включать:
   - проводную синхронизацию;
   - критические состояния;
   - обычные групповые данные;
   - полную резервную передачу.
2. Ввести режим `SYNC_PRIORITY`, в котором sync и аварийные события имеют
   гарантированный временной слот.
3. Ввести режим `SYNC_ONLY`, не отключающий саму шину и диагностику.
4. Изменять частоту sync без пересборки firmware в подтверждённом безопасном
   диапазоне.
5. Передавать в status фактически применённую частоту, текущее качество sync,
   величину последней коррекции и возраст последнего sync.
6. Автоматически вернуть полную проводную передачу по watchdog, если Raspberry
   Pi перестала подтверждать работоспособность IP-канала.
7. Использовать lease: Raspberry Pi периодически подтверждает `IP_DATA_OK`, а
   STM32 разрешает `SYNC_ONLY` только пока lease действителен.
8. Сделать переход `FULL_WIRE ↔ SYNC_PRIORITY/SYNC_ONLY` идемпотентным и
   подтверждаемым readback-статусом.
9. Не сбрасывать ADC, DMA, sample counter и sync epoch при смене транспорта.
10. Кратковременно допускать дублирование данных на двух каналах, чтобы
    принимающая сторона могла выполнить переход без разрыва.

`SYNC_ONLY` является исследовательским названием. Минимальные аварийные и
диагностические сообщения могут и должны остаться на проводе, если этого
требует безопасность.

### 4.6. Диагностическая firmware для измерений

Для принятия решения желательно получить тестовую firmware или debug mode со
следующими функциями:

- GPIO toggle на master в момент формирования sync;
- GPIO toggle на slave в момент hardware capture/приёма sync;
- GPIO toggle на master и slave в момент ADC trigger;
- опциональный GPIO toggle при готовности DMA/USB-кадра;
- счётчики sync, пропусков, коррекций, CRC, повторов и max jitter;
- выдача текущего timer offset и оценённого drift;
- настраиваемая частота sync;
- раздельные режимы полной нагрузки шины и sync-only;
- идентичный формат данных во всех тестовых режимах, чтобы результаты можно
  было сравнивать автоматически.

## 5. Требуемый ответ от STM32-команды

Результатом запроса должны быть:

1. заполненная таблица физических и временных параметров;
2. описание форматов всех проводных sync/data/status пакетов;
3. временная диаграмма `master timer → wire → slave capture → ADC trigger`;
4. расчёт и измерение загрузки проводной шины;
5. описание timestamp/sample counter в USB-кадре;
6. список уже доступных диагностических счётчиков;
7. оценка трудоёмкости `SYNC_PRIORITY`, `SYNC_ONLY` и watchdog возврата;
8. безопасный диапазон тестовых частот sync;
9. firmware version/build ID, на которой выполнены измерения;
10. бинарный лог или CSV не менее чем за 30 минут для режима полной нагрузки и
    режима без объёмных проводных данных.

## 6. Целевая архитектура служебного канала

### 6.1. Роли каналов

| Канал | Основная роль | Поведение при отказе |
|---|---|---|
| Провод STM32 | Аппаратная синхронизация, аварийные состояния, резерв данных | Всегда остаётся активным |
| Ethernet | Предпочтительный IP-транспорт данных при наличии link | Переход на Wi-Fi или провод |
| Wi-Fi | Служебный радиоканал данных и управления группы | Переход на Ethernet или провод |
| Bluetooth | Первичная настройка/поиск/восстановление, не основной ADC transport | Не влияет на измерение |

Рекомендуемый приоритет объёмного транспорта по умолчанию:

```text
Ethernet → Wi-Fi → проводной полный обмен
```

Приоритет должен быть настраиваемым. Проводная синхронизация работает при любом
из выбранных транспортов данных.

### 6.2. Режимы

1. `WIRE_FULL` — синхронизация и все данные идут по проводу. Безопасный default
   при запуске и любой неопределённости.
2. `HYBRID_ETH` — проводная синхронизация/критические статусы, объёмные данные по
   Ethernet.
3. `HYBRID_WIFI` — проводная синхронизация/критические статусы, объёмные данные по
   Wi-Fi.
4. `MIRROR_TEST` — данные параллельно идут по проводу и IP для сравнения. Только
   испытательный режим.
5. `DEGRADED_WIRE` — IP-каналы потеряны, система автоматически вернулась к
   полному проводу и сообщает причину.

Полный беспроводной режим синхронизации не является целью первого этапа. Его
можно исследовать позднее, но провод всё равно остаётся резервом.

### 6.3. Разделение процессов на Raspberry Pi

Текущий BMI30 core является владельцем USB-потока. Новый сетевой сервис не
должен открывать USB вторым процессом.

Предлагаемая схема:

```text
STM32 → существующий USB reader/core → локальный IPC → bmi30-data-link service
                                                    ├→ Ethernet
                                                    └→ Wi-Fi
```

- core публикует неизменяемый кадр и метаданные через локальный Unix socket или
  другой ограниченный IPC;
- отдельный `bmi30-data-link` отвечает за сеть, reconnect, heartbeat, буферы и
  метрики;
- ошибка сетевого сервиса не должна останавливать локальное измерение,
  детектирование, звук и индикацию;
- на первом прототипе допустима интеграция publisher в core, но сетевые ожидания
  никогда не должны выполняться в USB reader thread.

### 6.4. Топология группы

Для первого этапа рекомендуется star topology:

- каждый BMI30 отправляет измерения выбранному координатору;
- координатор выравнивает данные и выполняет групповую обработку;
- обратно рассылается компактный общий результат;
- all-to-all поток сырых данных не используется, чтобы нагрузка не росла как
  квадрат числа узлов;
- роль STM32 sync master, роль сетевого координатора и роль Internet gateway
  хранятся раздельно, хотя могут быть назначены одному прибору.

### 6.5. Формат сетевого кадра

Минимальные поля будущего бинарного кадра:

| Поле | Назначение |
|---|---|
| `magic`, `protocol_version` | Проверка формата и совместимость |
| `group_id`, `node_id` | Источник и группа |
| `boot_id`, `sync_epoch` | Защита от старых/повторных сеансов |
| `transport_epoch` | Однозначная смена Ethernet/Wi-Fi/провод |
| `frame_seq` | Потери и порядок кадров |
| `first_sample_counter` | Точное временное выравнивание |
| `stm32_timestamp` | Дополнительная аппаратная метка |
| `sample_rate_num/den` | Фактическая частота семплирования |
| `channel_mask` | Состав ADC-каналов |
| `samples_per_channel` | Размер данных |
| `averaging_factor` | Интерпретация рабочего кадра |
| `sync_quality`, `flags` | Состояние проводной синхронизации |
| `payload_length` | Контроль границ |
| `payload_crc32c` | Целостность |

Network arrival time разрешено использовать только для диагностики задержки.
Выравнивание антенн выполняется по `sync_epoch + first_sample_counter`.

### 6.6. Транспортный протокол

На прототипе сравнить два варианта:

1. UDP unicast с sequence number, CRC, reorder buffer и локальным кольцевым
   буфером для недавних кадров;
2. TCP для простого гарантированного потока при низкой нагрузке.

Предварительно для непрерывных измерений предпочтителен UDP unicast, потому что
потеря одного кадра не задерживает все последующие. Для команд, конфигурации и
подтверждений нужен надёжный канал с authentication и acknowledgements. Решение
принимается после измерения, а не только по теоретической скорости.

Wi-Fi multicast не использовать для основного сырого потока на первом этапе:
он часто не имеет подтверждений и может передаваться на низкой basic rate.

## 7. Безопасное переключение каналов

### 7.1. Принцип fail-safe

Безопасное состояние любого прибора — `WIRE_FULL`.

Переход к `HYBRID_ETH/HYBRID_WIFI` разрешён только при выполнении всех условий:

- проводная синхронизация валидна;
- IP-интерфейс имеет link и адрес;
- координатор подтверждён;
- двусторонний heartbeat стабилен заданное время;
- принимающая сторона подтверждает правильные `node_id`, `sync_epoch` и
  непрерывный sample counter;
- STM32 получила команду режима и readback совпадает с запросом.

### 7.2. Lease/watchdog

Для защиты от зависания Raspberry Pi предлагается firmware-механизм:

1. Raspberry Pi включает сокращённую проводную передачу с ограниченным lease.
2. Пока IP-канал исправен, Raspberry Pi продлевает lease локальной USB-командой.
3. При остановке процесса, потере сети, зависании ОС или USB lease истекает.
4. STM32 самостоятельно возвращает `WIRE_FULL`.
5. Факт и причина возврата доступны в status.

Если firmware-watchdog сразу реализовать нельзя, первый прототип использует
host watchdog, но не считается готовым к штатной эксплуатации.

### 7.3. Переход без потери данных

Последовательность переключения:

1. Новый канал запускается в mirror/catch-up режиме.
2. Получатель подтверждает непрерывность sample counter.
3. Увеличивается `transport_epoch`.
4. Новый канал становится primary.
5. Старый канал некоторое время передаёт перекрывающиеся кадры.
6. Получатель удаляет дубликаты по `boot_id + sync_epoch + sample_counter`.
7. Только после подтверждения провод переводится в сокращённый режим.

При отказе IP выполняется обратная последовательность, но включение полного
провода имеет приоритет и не ждёт восстановления сети.

## 8. Расчёт пропускной способности

Расчёт выполнять по фактическому USB-кадру:

```text
payload_bps = frames_per_second
              × samples_per_channel
              × channel_count
              × bytes_per_sample
network_bps = payload_bps + frame_headers + transport_overhead
group_bps = sum(network_bps for all active nodes)
```

Для примера, без утверждения числа каналов:

- один канал: `50 × 200 × 2 = 20 000 байт/с`;
- два канала: `50 × 200 × 2 × 2 = 40 000 байт/с`;
- к этому добавляются заголовки и диагностические сообщения.

Нужно отдельно уточнить, относится ли 50 Гц к каждому каналу, паре A/B или уже
усреднённому объединённому кадру. Для sizing использовать измеренный USB bitrate
в худшем режиме 600 семплов и суммарное число приборов. Целевой IP-транспорт
должен иметь не менее двукратного запаса по устойчивой пропускной способности.

## 9. План разработки и испытаний

### Этап 0. Ответы STM32 и критерии

Результат:

- заполнены разделы 4 и 5;
- утверждены `T_event` и `T_sample`;
- известна реальная загрузка провода и USB;
- известен безопасный диапазон частоты sync;
- определён тестовый комплект минимум из двух BMI30.

Без этого этапа нельзя принимать решение об изменении firmware sync.

### Этап 1. Базовое измерение существующего провода

Измерить при полной текущей нагрузке:

- временную разницу master/slave ADC trigger осциллографом или logic analyzer;
- среднюю, p95, p99, максимум и выбросы;
- drift между sync-событиями;
- загрузку шины, очереди, CRC/retry/missed sync;
- результат на 2, 4 и максимально доступном числе приборов;
- работу не менее 30 минут, затем длительный прогон 8–24 часа.

Сохранить сырые измерения и firmware build ID.

### Этап 2. Эксперимент с разгруженным проводом

Повторить идентичный тест в режимах:

1. полная существующая передача;
2. sync с абсолютным приоритетом;
3. sync + минимальные критические статусы;
4. исследовательский sync-only;
5. несколько подтверждённых STM32-командой частот sync.

Сравнить не только среднюю ошибку, но максимум и хвост распределения. Если
разгрузка не улучшает `T_sample`, искать hardware/firmware источник jitter, а не
переносить данные в радио ради самой синхронизации.

### Этап 3. Наблюдающий IP-прототип

- создать локальный IPC из BMI30 core без второго открытия USB;
- передать сетевые кадры от одного узла координатору;
- провод оставить в полном текущем режиме;
- сетевые данные только записывать и сравнивать, не использовать для управления;
- проверить Ethernet и Wi-Fi отдельно;
- сверить каждый IP-кадр с исходным USB/проводным кадром по sequence, sample
  counter и CRC.

### Этап 4. Mirror test двух и более BMI30

- одновременно писать проводной и IP-поток;
- проверить потери, дубли, reorder, p50/p95/p99 latency и максимальную паузу;
- проверить 2,4 ГГц/5 ГГц в поддерживаемых аппаратурой диапазонах;
- проверить влияние Bluetooth coexistence;
- добавить контролируемые помехи и параллельную загрузку интернета;
- проверить CPU, RAM, температуру и отсутствие влияния на USB reader/detector.

### Этап 5. Гибридный режим

- STM32 проводит синхронизацию и критические статусы;
- выбранный IP-канал переносит объёмные данные;
- включить readback режима STM32;
- включить lease/watchdog;
- подтвердить, что разгрузка провода даёт измеримое улучшение либо как минимум
  не ухудшает синхронизацию;
- локальная детекция должна продолжать работать при любой сетевой ошибке.

### Этап 6. Автоматический failover

Проверить переходы:

- Ethernet → Wi-Fi;
- Wi-Fi → Ethernet;
- Ethernet → провод;
- Wi-Fi → провод;
- оба IP-канала → провод;
- провод → восстановленный IP после стабильного probation interval;
- перезапуск data-link service;
- зависание/перезапуск Raspberry Pi;
- перезапуск STM32;
- потеря координатора и смена сетевого координатора;
- односторонняя потеря связи и network partition.

Для каждого перехода проверить непрерывность `sync_epoch/sample_counter`, время
обнаружения, время возврата, число пропущенных/дублированных кадров и отсутствие
ложных групповых событий.

### Этап 7. Подготовка антенной обработки

- реализовать reorder/alignment buffer координатора;
- группировать кадры по `sync_epoch + sample_counter`;
- помечать missing/stale, не заменяя отсутствующие данные молча нулями;
- измерить постоянную задержку и gain/phase каждого тракта;
- сначала объединять результаты детектора;
- затем отдельно испытать корреляцию сырых данных;
- хранить локальный кольцевой буфер сырых ADC и передавать расширенное окно по
  событию, если постоянный сырой поток не нужен.

### Этап 8. Internet gateway

После стабилизации служебного канала один BMI30 может стать Internet gateway:

- отдельная групповая подсеть;
- NAT, DHCP и firewall;
- предпочтительно отдельный интерфейс для внешнего интернета: Ethernet, LTE или
  второй Wi-Fi adapter;
- ограничение/QoS интернет-трафика относительно служебных данных;
- отсутствие зависимости STM32 sync master от роли Internet gateway;
- при потере gateway локальная группа и проводная синхронизация продолжают
  работать.

### Этап 9. Интерфейс и эксплуатация

В Portal/Utilities показывать:

- активный транспорт данных и резерв;
- состояние Ethernet, Wi-Fi и провода;
- STM32 sync quality, age, missed count и текущую частоту;
- `sync_epoch`, `transport_epoch`, coordinator и gateway;
- bitrate, loss, reorder, latency и buffer depth;
- причину последнего failover;
- состояние lease/watchdog;
- ручной безопасный выбор `WIRE_FULL`, диагностического mirror и автоматического
  режима.

Ручной режим не должен позволять полностью отключить проводную синхронизацию.

## 10. Критерии приёмки пилота

Числовые значения `T_event` и `T_sample` заполняются после ответа STM32-команды и
измерения базовой системы. Остальные минимальные критерии:

1. Проводная синхронизация активна во всех штатных режимах.
2. При недоступности Ethernet и Wi-Fi система автоматически работает по
   проводу без ручного вмешательства.
3. Смена транспорта не сбрасывает общую шкалу семплов.
4. Все потери и дубликаты обнаруживаются sequence/sample counter.
5. Повреждённые пакеты отклоняются по CRC.
6. Сетевой сервис не блокирует USB reader и локальную обработку.
7. Устойчивая пропускная способность IP имеет не менее 2× запаса относительно
   измеренного суммарного USB-потока выбранной группы.
8. p99 сетевой задержки укладывается в настроенный alignment buffer; отдельный
   поздний пакет не останавливает последующие.
9. Failover и failback не создают ложного события детектора.
10. STM32 watchdog возвращает полный провод при остановке Raspberry Pi или
    сетевого сервиса.
11. Гибридный режим улучшает проводную синхронизацию либо сохраняет её не хуже
    baseline; результат подтверждён одинаковым измерительным методом.
12. Длительный прогон 24 часа не даёт необъяснённых разрывов, смен epoch или
    накопления drift.

## 11. Решение после испытаний

После этапов 0–6 оформить таблицу решения:

| Вариант | Когда выбирать |
|---|---|
| Провод sync + провод data | IP не даёт устойчивого преимущества или нужен самый простой режим |
| Провод priority sync + минимальные данные, IP bulk | Рекомендуемый гибрид, если IP стабилен и разгрузка уменьшает jitter |
| Провод sync + IP data, провод data standby | Если watchdog/failover доказан и требуется максимальная ёмкость провода для sync |
| Радиосинхронизация с проводным резервом | Только отдельный будущий эксперимент после доказанной точности аппаратных timestamps |

Решение принимается раздельно по трём показателям:

- точность/джиттер синхронизации STM32;
- надёжность и непрерывность данных при отказах;
- пропускная способность и масштабирование группы.

Высокая скорость Wi-Fi сама по себе не является основанием переносить на него
аппаратную синхронизацию. Одновременно невысокая рабочая скорость данных не
является основанием отказываться от IP: его запас полезен для сырых записей,
диагностики, групповой обработки и будущего Internet gateway.

## 12. Основные риски

- использование времени прихода Linux/IP-пакета вместо STM32 timestamp;
- неуточнённая семантика существующего timestamp;
- переключение канала со сбросом sample counter;
- зависание Raspberry Pi после отключения проводных данных без firmware lease;
- дубли и старые пакеты после reconnect;
- Wi-Fi jitter при помехах или совместной работе Bluetooth;
- один Wi-Fi radio одновременно обслуживает служебную группу и внешний AP/STA;
- head-of-line blocking надёжного транспорта;
- связь ролей sync master, coordinator и gateway в одну неотказоустойчивую роль;
- увеличение частоты sync без понимания timer/ISR jitter;
- скрытая перегрузка STM32 interrupt/DMA при добавлении диагностики;
- масштабирование all-to-all вместо star topology.

Каждый из этих рисков должен иметь измеряемый status/counter и отдельный тест.
