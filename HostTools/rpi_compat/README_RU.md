# Совместимость нового Raspberry с прежней STM32

Выпуск Raspberry `2026-10-23-1435`, база `2026-10-23-1332`.
STM32 при установке этого выпуска не прошивается.

`usb_vendor/capabilities.py` использует существующий USB-дескриптор владельца.
Явный STALL/PIPE на корректном запросе дополнительной функции запоминается
как отсутствие функции на текущем соединении. Тайм-аут, отключение USB или
повреждённый ответ не объявляются отсутствием функции. При новом дескрипторе
или новом времени подключения проверка выполняется заново. Чтение возможностей
через API само по себе не запускает USB-опрос.

- Сохранённые TX-фазы не блокируют START_STREAM, если TXP1 отсутствует.
  Сохранённые предпочтения остаются в конфигурации. Неподдерживаемый SET
  не считается выполненным и не сохраняется.
- При отсутствии RLY1 реле отмечено недоступным; повторные обращения к нему
  не занимают USB. Команда завершается явным отказом, не тайм-аутом очереди.
- При отсутствии COM1/K1 он пропускается. Для старой STM32 не отправляется ACK.
- TX-фазы в интерфейсе недоступны при отсутствии этой функции, при этом
  автоадаптация RX на Raspberry остаётся независимой и доступной.
- Текущие возможности видны в Core `/api/status` → `stm32_capabilities`.
  Неопрошенная функция имеет `supported: null`, отсутствующая — `false`,
  подтверждённая ответом правильного формата — `true`.

Проверен сохранённый STM32 `1.2.53 r5`, сборка 29.09.2026 14:58:32,
tag `bmi30-fw-1.2.53-r5-2026-09-29`: все 29 основных кодов запросов текущего
хоста есть в старом протоколе; 9 сборщиков пакетов и 32-байтовый заголовок ADC
совпадают. Фильтр роста подтверждений и служебные Wi-Fi/Bluetooth выполняются
на Raspberry. K1 требует STM32 1.2.54+, исправление физического TX1/PC7 на
BMI30_1v1_02 — 1.2.56. Наличие старой команды TX1 не исправляет старую разводку
программного GPIO. Эти аппаратные ограничения остаются.

27 Python-проверок: 13 совместимости и 14 регрессий реле. Отдельно прошли
5 проверок протокола старой версии и DOM-проверка фактического JavaScript
из Python f-string. Реальная STM32 1.2.53 с новым Raspberry в этой работе
не подключалась: отсутствие функций моделировалось ответами STALL/PIPE.

Подготовка воспроизводимых исходников тестов:

```text
python HostTools/rpi_compat/prepare_candidate.py
python HostTools/rpi_compat/test_compatibility.py
```

Установка проверена на USB M02/S07 с существующей STM32 1.2.56. eMMC обоих
приборов обновлены через chroot и проверены повторным чтением после remount,
без загрузки с них. На первой попытке M02 проверка здоровья откатила пакет
из-за нестабильного запуска USB; повторная установка прошла с увеличенным
ожиданием без ослабления требований к потоку/API. Настройки каждого носителя
сохранены, движок детектора побайтно совпадает с 1332. Подробные результаты
находятся в `FirmwareReleases/RaspberryPi/2026-10-23-1435/deployment/`.
