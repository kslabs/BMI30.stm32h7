# BMI30: служебный обмен по Wi-Fi и Bluetooth Classic

Версия сети `0.2.4`, протокол `2`, пакет `2026-10-23-service-transports-r2`.
На групповой странице добавлен сохраняемый выбор Wi-Fi, Bluetooth, обоих каналов или выключения для текущего прибора. Выбор относится к групповой телеметрии и командам; Интернет и доступ к странице сохраняются. Для Bluetooth-only совместимый режим нужно выбрать на обоих приборах. Локальная строка показывает свежие фактически используемые каналы; при отсутствии обмена явно указано ожидание связи, при выключении — Service off. Слово BMI30 из названия канала удалено.
Проверенные Bluetooth-адреса сохраняются в отдельном файле состояния. Собственный адрес передаётся в подписанной свежей групповой записи: Wi-Fi помогает найти Bluetooth-партнёра даже после удаления временных объектов BlueZ. Каждый вызов заново проверяет идентификатор и криптографическое подтверждение; адрес является только подсказкой.
R2 исправил типизацию D-Bus RegisterProfile/UnregisterProfile. R3 отбрасывает телеметрию с истёкшим запросом свежести, сохраняя Bluetooth-соединение для следующего свежего сообщения; просроченные данные по-прежнему не принимаются. Обе проблемы обнаружены на настоящем BlueZ. Результаты испытаний и установки на M02/S07 находятся в отдельном отчёте развёртывания.

## Поведение

- Wi-Fi и Bluetooth работают параллельно с общей CM5-идентичностью. Для передачи состояния и разрешённых групповых команд Интернет не нужен.
- Bluetooth использует Classic BR/EDR и отдельный профиль RFCOMM. Номинальный набор — 79 радиоканалов по 1 МГц; адаптивный выбор AFH оставлен контроллеру. RFCOMM-порт 22 — логический номер службы, он не задаёт радиочастоту.
- При равной длине маршрута предпочтителен свежий путь Wi-Fi. Сохраняется альтернативный путь Bluetooth. При ошибке/тайм-ауте Wi-Fi команда отправляется по альтернативному пути с прежним command_id и в пределах исходного срока действия.
- В групповой странице служебный транспорт обозначен `Wi-Fi` или `Bluetooth`. Адрес Bluetooth не подставляется вместо IP или номера CM5.
- Авторизация по общему секретному ключу группы: HMAC, AES-GCM, двусторонний обмен случайными запросами, привязка ответов к текущему сеансу. Обнаруженное имя и MAC являются только подсказками для соединения.
- Данные стареют по локальному монотонному таймеру. При пересылке возраст накапливается; старый пакет или событие ADC не омолаживает прежний результат. Повторные команды используют общую постоянную историю выполнения для обоих транспортов.
- Календарные метки остаются для журналов. Сравнения часов разных приборов, NTP и проверки доступности Интернета исключены из определения свежести служебных сообщений.
- Заголовок Raspberry Pi читается из аппаратного serial текущего CM5. STM32 UID остаётся отдельным полем.

Bluetooth не передаёт Интернет и не переносит поток сырых ADC. Существующие настройки аудио/HID, сопряжения и доверенных устройств сохраняются. Служебный профиль использует прикладное шифрование без автоматического сопряжения и без общей команды `trust`. BlueZ получает отдельную сессию поиска BR/EDR: 12 секунд с интервалом 30–40 секунд. Первое обнаружение занимает время; уже установленные соединения поддерживаются постоянно. Запрос видимости ограничен собственной сессией поиска; общие настройки Powered, Pairable, Alias и DiscoverableTimeout не меняются. Выключенный радиомодуль автоматически не включается.

Для встроенного CM5 Wi-Fi и Bluetooth используют общий радиомодуль/антенный тракт. Второй транспорт устраняет зависимость от локальной IP-сети, но не создаёт независимую антенну и не гарантирует связь при широкополосной помехе. Измерение задержек, дальности, четырёх одновременных приборов и совместной работы с аудио/пультом необходимо выполнить на реальных устройствах.

## Установка на конкретный прибор

Обновить все четыре устройства одной группы. Протокол 2 намеренно не принимает протокол 1. Во время смешанной установки старые и новые устройства не обмениваются служебными сообщениями.

Требуются существующие `bmi30-network`, `bmi30-hotspot-info`, работающий `bmi30-core`, активный источник портала в `host/bmi30_split_active_version.env`, установленный BlueZ, системные Python-пакеты `cryptography`, `dbus` и `gi`. Для включённого Bluetooth-служебного канала адаптер должен быть включён пользователем. Установщик ничего не скачивает, не меняет Wi-Fi-регион, мощность, NetworkManager-профили, пароли, настройки детектора или STM32.

После копирования архива на выбранный прибор распаковать его и сначала выполнить проверку, подставив номер именно его CM5:

```sh
tar -xzf BMI30-Network-service-transports-2026-10-23-r2.tar.gz
cd bmi30-clockless
sudo /usr/bin/python3 install_clockless.py --expected-id BMI30-27448D72B
sudo /usr/bin/python3 install_clockless.py --expected-id BMI30-27448D72B --apply
```

Указанный номер — S12 из разбираемого случая; на остальных приборах использовать их аппаратные номера. До записи проверяются все установленные/активные/зеркальные исходники портала и Python-модули сети. Неподдерживаемая версия портала или несовпадение физического номера останавливает установку. Подготовленные варианты портала проверены на локальных исходниках 2026-10-21-1501 и 2026-10-21-1819; это не доказывает совместимость произвольной более старой установленной версии.

Оригиналы сохраняются в `/var/backups/bmi30-clockless/<время>`, файлы заменяются атомарно. Перезапускаются сеть и портал. Проверяются аппаратная идентичность, версия протокола, регистрация Bluetooth-профиля, сохранение PID ядра и контрольных сумм конфигурации. При ошибке восстанавливаются прежние файлы, новые модули удаляются, сеть и портал запускаются повторно. При обрыве питания во время записи нужны сохранённые оригиналы и manifest из каталога резервной копии; автоматический откат покрывает ошибки процесса установки, а не потерю питания.

Основное ядро не перезапускается. Новый формат локальных owner-событий совместим со старым отправителем; исходники помощника получают монотонные метки для следующего штатного запуска ядра. Журналы установщика содержат пути и хеши, без секретов.

## Настройка Bluetooth-службы

В существующем `/etc/bmi30-network/config.json` необязательный раздел `bluetooth` допускает `enabled` (по умолчанию true), `adapter` (например `hci0`) и `peers` — список известных адресов с необязательным ожидаемым CM5-id. Это позволяет соединяться по известным адресам без ожидания нового поиска. Редактировать только на выбранном приборе; ключ группы и остальные поля сохранять. Установщик этот раздел не переписывает.

`http://127.0.0.1:8791/status` содержит `bluetooth.state`, режим `classic-bredr`, `nominal_channels:79` и список аутентифицированных соседей. Состояние `listening` означает регистрацию профиля, а не доказанную радиосвязь со всеми соседями. `adapter-off` означает выключенный адаптер, `unavailable` — отсутствующую зависимость или ошибку BlueZ. Регион Японии и внедиапазонные частоты этим пакетом не устанавливаются.

## Проверки и границы доказательства

Проверены противоположные календарные даты и скачки времени, локальное истечение TTL, защита от повторов и перезапуска, относительный возраст при ретрансляции, сохранение коротких фронтов датчиков, реальный HTTP/AES-GCM обмен, зашифрованные двусторонние потоки Bluetooth-протокола через локальные сокеты, переход Wi-Fi → Bluetooth при потере ответа и единственное выполнение команды, контракт BlueZ на поддельной D-Bus шине, страницы портала, установка и принудительный откат.

Локальные сокеты и поддельная D-Bus шина не проверяют радиомодуль, работу ядра RFCOMM/BlueZ на конкретном образе Raspberry Pi OS, дальность или помехоустойчивость. Итоговые счётчики проверок находятся в `validation.json` рядом с архивом. Испытания на реальном оборудовании и установка не выполнены.
