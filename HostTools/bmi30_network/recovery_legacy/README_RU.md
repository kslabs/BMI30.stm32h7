# Восстановление четвёртой BMI30 через три доступные платы (история r1)

Пакет `2026-10-27-legacy-recovery-r1`; сеть `0.1.13-recovery1`.
Для исходного комплекта RPi `2026-10-05-192357` / STM32 `1.2.53`.

Установка разрешена только на эти три CM5:

- `BMI30-05AB38E6A`
- `BMI30-D5507EDFC`
- `BMI30-7AA5CED27`

Приёмник остаётся без обновления: `BMI30-27448D72B`, полный serial
`A043B0627448D72B` (исторически S12). На него этот пакет не устанавливается.

## Как работает восстановление

Старая плата сама пытается посетить заранее известную точку Wi-Fi другой платы
и выполняет `POST /exchange`. В запросе уже есть её время, зашифрованное общим
ключом группы, и подписанная идентификация. Заплатка на доступной плате может
принять такой запрос при несовпадающих календарных датах. Ответ использует
старый протокол 1, старые подпись и AES-GCM и время самого получателя.
Настройки внешнего Wi-Fi в ответе также получают дату, допустимую для старого
приёмника. Системные часы обеих плат не меняются.

Восстановление разрешено только указанному приёмнику с правильным существующим
ключом группы. В ответ попадают известные службе внешние Wi-Fi-настройки;
пароли не выводятся в журналы, HTTP status или отчёт. Входящие старые команды
не получают обход проверки времени, старые маршруты через восстановительный
обработчик не импортируются, новый код не открывает USB/RS-485.

Нужна хотя бы кратковременная Wi-Fi/IP-связь между приёмником и одной из трёх
плат. Видимый SSID и работающий RS-485 этого не доказывают. При неисправной
ассоциации Wi-Fi, неизвестном пароле соседнего AP, разных ключах группы,
выключенном автоматическом поиске на четвёртой плате или отсутствии известных
соседей сам запрос не придёт. Заплатка не исправляет радио удалённо без связи.

До установки на одной из трёх плат должен быть настроен и сохранён нужный
внешний Wi-Fi. Служба должна уже знать его настройки. Если ни одна из плат
не знает пароль внешней сети, передавать нечего.

## Строгая граница изменений

В активной системе меняются только:

1. `/opt/bmi30-network/service.py` — версия, создание обработчика, статус и
   резервная обработка запроса `/exchange`.
2. `/opt/bmi30-network/legacy_recovery.py` — новый адресный обработчик.

Исходники маршрутизации, сканирования, переключения каналов, обнаружения соседей,
основного обмена остальных приборов и групповых команд сохраняются. Это
проверяется сравнением AST методов `Agent`, а полный diff находится в `review`.
Протокол 1 сохраняется. Перехода на протокол 2, обновления Bluetooth, STM32,
детектора, портала, настроек Wi-Fi/хотспота или загрузки с другого носителя нет.
Перезапускается только `bmi30-network`. Основное ядро и портал продолжают работу.

Исходная версия `service.py` проверяется по SHA-256 настоящего архива
`2026-10-05-network-13`. Чужая версия, несовпадение CM5/сетевого идентификатора,
изменённые файлы или посторонний модуль с таким именем останавливают установку.

## Установка и откат

Установщик предназначен для оператора, имеющего существующий доверенный доступ
к выбранной плате. Это архив сетевой заплатки; загрузка его в обычное меню
полной RPi-прошивки без интеграции с серверным установщиком не поддерживается.
Он пока не опубликован как полная прошивка на BMI30-сервере.

После распаковки на выбранной Raspberry выполнить проверку без записи:

```sh
sudo /usr/bin/python3 install_recovery.py --expected-id BMI30-05AB38E6A
```

Для двух остальных использовать их точные номера. Проверить результат
`stage=dry-run`, после чего на этом же приборе выполнить:

```sh
sudo /usr/bin/python3 install_recovery.py --expected-id BMI30-05AB38E6A --apply
```

До записи создаётся резервная копия в `/var/backups/bmi30-network-recovery/…`
и отдельный таймер systemd. При исключении или неуспешной проверке службы/портала
старые файлы возвращаются сразу. При обрыве SSH или завершении установщика
таймер через 300 секунд запускает сохранённый в резервной копии откат.

После `stage=awaiting-external-commit` проверить с компьютера клиента обычный
портал, доступ к версии/обновлению и `/status` службы. Затем в новом подключении
к этой плате подтвердить установку, используя путь `backup` из результата:

```sh
sudo /usr/bin/python3 install_recovery.py --expected-id BMI30-05AB38E6A --commit /var/backups/bmi30-network-recovery/TRANSACTION
```

Подтверждение отменяет таймер. Поздний уже запущенный автоматический откат
не отменит подтверждённую установку. Устанавливать последовательно,
по одной плате, сохраняя доступ через остальные.

После подтверждения ручной откат остаётся доступен:

```sh
sudo /usr/bin/python3 /var/backups/bmi30-network-recovery/TRANSACTION/rollback_tool.py --expected-id BMI30-05AB38E6A --rollback /var/backups/bmi30-network-recovery/TRANSACTION
```

Ручной откат возвращает только два файла заплатки и перезапускает сетевую службу.
Если тем временем установлена другая прошивка или изменились сетевые зависимости,
он выдаёт `superseded-by-another-update` и не переписывает её файлы. Текущий
механизм полной перепрошивки, портал, токены сервера и конфигурация не меняются.
Таймер transient: автоматический отсчёт не сохраняется после перезагрузки;
резервная копия и ручной откат сохраняются. Подтверждение или проверку отката
нужно закончить до намеренной перезагрузки.

## Как увидеть результат

На доступной плате `http://<её-IP>:8791/status` содержит `legacy_recovery`:

- `waiting-for-target` — подходящего запроса ещё не было.
- `no-shared-wifi-settings` — запрос пришёл, но службе нечего передать.
- `settings-offered` — подготовлен ответ с настройками; принятие ещё не доказано.
- `credentials-confirmed` — следующий запрос приёмника уже содержал эти настройки.
- `future-timestamp-conflict` — у приёмника другая версия пароля с датой из его
  будущего; старый код не разрешает безопасно её заменить таким ответом.

Последнее состояние не означает, что пароль выведен в status: сравнение идёт
внутри зашифрованного обмена. `credentials-confirmed` доказывает наличие настроек
в памяти приёмника, но не самостоятельную проверку записи на носитель, подключения
к роутеру или Интернета. Для завершения восстановления проверить появление
четвёртой платы в LAN/на сервере, доступ к её порталу и повторить после её
штатной перезагрузки. Старый локальный NM-профиль с тем же SSID и неверным паролем
также может мешать выбору переданных настроек; это отдельный случай диагностики.

## Выполненная проверка

Неизменённые `contact`, `remember_secret` и `Protocol` из настоящего октябрьского
архива использованы в локальном HTTP-испытании. Клиент с датой 1970 года принял
и записал настройки от отправителя с датой 2033 года; проверено и обратное
направление. Исходный сервер при том же расхождении обмен отвергает.

Проверены обычный обмен остальных плат, неверный ключ/идентификатор, повреждение
пакета, повтор запроса после смены даты, подтверждение настроек следующим
запросом, конфликт старой будущей даты пароля, принудительный откат, отсутствие
подтверждения, подтверждение до таймера и установка более новой прошивки.
Команды systemd в тестах имитируются. Реальный Wi-Fi, systemd на клиентских CM5,
автоподключение четвёртой платы и её Интернет ещё не проверены.
