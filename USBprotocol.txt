# USB VENDOR ПРОТОКОЛ (версия 1.0)
 
Документ фиксирует формат кадров, команды управления и инварианты хоста/прошивки. 
Цель — исключить регрессии и «забывание» деталей при дальнейших изменениях.

## 1. Идентификация устройства
VID: 0xCAFE  
PID: 0x4001  
Composite: CDC + Vendor (интерфейс vendor обычно №2).  
Bulk endpoints (alt0):
- OUT: 0x03 (host → device, команды)
- IN : 0x83 (device → host, поток и статус / тестовый кадр)

## 2. Формат потокового кадра
Каждый кадр = 32‑байтовый заголовок `VendorHdr` + payload (сырые сэмплы) + (опц.) CRC16.

```
Offset Size  Field            Type      Описание
0      2     magic            u16       0xA55A (LE)
2      1     version          u8        Текущая версия структуры (1)
3      1     flags            u8        Биты, см. ниже
4      4     seq              u32       Номер логической последовательности (кадровая пара)
8      4     timestamp        u32       Временная метка (мс или device ticks*)
12     2     total_samples    u16       Кол-во сэмплов в payload (для данного ADC кадра)
14     2     zone_count       u16       Зарезервировано (0)
16     4     zone1_offset     u32       Зарезервировано (0)
20     4     zone1_length     u32       Зарезервировано (0)
24     4     reserved         u32       (0)
28     2     reserved2        u16       (0)
30     2     crc16            u16       CRC16-CCITT-FALSE заголовок+payload (при флаге CRC)
```
Endian: Little‑endian для всех многобайтовых полей.

Payload: массив `total_samples` значений по 2 байта (LE). (Т.е. размер payload = `2 * total_samples`).  
Флаг CRC (bit2) определяет присутствие и валидацию crc16. Если бит не установлен — поле crc16 может быть 0 (игнорируется).

### 2.1 Флаги `flags`
| Бит | Маска | Значение                    |
|-----|-------|----------------------------|
| 0   | 0x01  | Кадр ADC0                  |
| 1   | 0x02  | Кадр ADC1                  |
| 2   | 0x04  | CRC включён                |
| 7   | 0x80  | Тестовый кадровый маркер   |

Комбинации: рабочие кадры используют ровно один из {0x01,0x02} (+ возможно 0x04). Тестовый кадр: 0x81 (ADC0 + TEST).  
Флаги 0x01 и 0x02 одного и того же `seq` образуют стерео‑пару. 

### 2.2 Последовательность и пары
`seq` инкрементируется после успешной отправки двух кадров (ADC0 и ADC1) для данной последовательности.  
Инвариант: для любого `seq` должно быть не более по одному кадру с флагом 0x01 и по одному с 0x02. Дубликаты запрещены.  
Хост проверяет: монотонность seq без дыр; приём пары -> счётчик стерео‑пар.

### 2.3 Фиксация размера (auto‑lock)
Алгоритм прошивки:
1. `cur_samples_per_frame` = 0 при старте.
2. Первый полный DMA кадр (или отдельный механизм) фиксирует значение `cur_samples_per_frame` и 
вычисляет `cur_expected_frame_size = 32 + 2*cur_samples_per_frame`.
3. Все следующие кадры должны иметь ровно `total_samples == cur_samples_per_frame`. 
Иначе — игнорируются (`dbg_partial_frame_abort++`).

Допустимые рабочие размеры на сегодня: 912 / 944 / 976 (примерные варианты).  
Тестовый кадр (8 сэмплов) НЕ фиксирует рабочий размер; хост игнорирует его при установке `exp_frame_size`.

## 3. Команды управления (bulk OUT на EP 0x03)
Каждая команда: первый байт = код, далее опциональный payload (не более 63 байт). 
Ответ (если предусмотрен) приходит как отдельный bulk IN пакет 
(может быть статусным коротким кадром или стандартным кадром, в зависимости от реализации).

| Код  | Имя             | Назначение | Payload OUT | Ответ IN |
|------|-----------------|------------|-------------|----------|
|0x14  | CMD_SET_PROFILE | Выбор профиля обработки/фильтра | 1 байт profile | (опц.) статус*
|0x13  | CMD_SET_FULL_MODE| 0=ROI, 1=FULL режим захвата    | 1 байт flag    | (опц.) статус*
|0x15  | CMD_SET_ROI_US  | Задание ROI по номеру семпла   | 4 байта (u32)  | (опц.) статус*
|0x1D  | CMD_SET_SYNC_MODE | Управление auto/forced ролью sync | 1 байт mode, опц. `node_id` для slave | нет
|0x1B  | CMD_SET_DC_ADAPT | Legacy управление DC-обучением | 1 байт: 0=FREEZE, 1=WORK | нет
|0x1F  | CMD_SET_DC_CONFIG | Настройка режимов скорости DC-компенсации | `DcConfigSetV1`, 20 байт | нет
|0x20  | CMD_START_STREAM| Запуск потока: отправить тестовый кадр + начать фиксацию размера | none | поток
|0x21  | CMD_STOP_STREAM | Остановка: прекращение потока, сброс внутренних флагов | none | статусная структура
|0x30  | CMD_GET_STATUS  | (Расширенный) запрос статуса     | none | статусная структура
|0x31  | CMD_GET_TEMP    | Получить температуру кристалла  | none | RSP_ACK + cmd + 2 байта (int16_t LE)
|0x32  | CMD_GET_VERSION | Получить версию прошивки        | none | RSP_ACK + cmd + 4 байта (major, minor, patch, build)
|0x33  | CMD_SET_TX_ENABLE | Persistent host-request TX200: 1 включает передачу, 0 выключает | 1 байт: 0/1 | (опц.) статус*
|0x38  | CMD_GET_LCD_STATUS | Снимок sync-индикатора LCD (`M/S/O`, число, цвет) | none | структура `LCDS` (24 байта)
|0x3A  | CMD_GET_DC_CONFIG | Снимок текущих настроек DC-компенсации | none | структура `DCCF` (40 байт)
|0x3D  | CMD_SET_RS485_ID | Временный локальный RS485 id | 1 байт: 0 или 1..31 | нет
|0x3E  | CMD_SET_RS485_IP | Локальный IPv4 для RS485 identity | 4 байта: `a,b,c,d` | нет
|0x3F  | CMD_REQUEST_RS485_IDENT | Запустить один master-scan ID/IP по RS485 | none | нет
|0x40  | CMD_GET_RS485_IDENT | Получить строку таблицы RS485 identity | EP0 IN: `wValue=node_id`, 0=local | структура `RID1` (32 байта)
|0x41  | CMD_SET_LCD_ROLE_OVERLAY | Разрешить/запретить крупную LCD-индикацию роли | `enable`, опц. `period_s,duration_s` | нет

`*` Статус после SET_* может быть отложен или не возвращаться — зависит от реализации.
Гарантированно возвращается после STOP и GET_STATUS.

## 3.1. Команда GET_TEMP (0x31) - Получение температуры

Команда 0x31 возвращает текущую температуру кристалла встроенного датчика STM32H723.

**Запрос (OUT → 0x03):**
- Один байт: `0x31`
- Без payload

**Ответ (IN ← 0x83):**
- 4 байта:
    - Byte 0: `0x80` (RSP_ACK)
    - Byte 1: `0x31` (echo команды)
    - Bytes 2-3: температура кристалла (int16_t, LE)

**Примеры:**
- `+28°C`: ответ `[0x80, 0x31, 0x1C, 0x00]` → 0x001C = 28
- `-10°C`: ответ `[0x80, 0x31, 0xF6, 0xFF]` → 0xFFF6 = -10 (дополнительный код)

**Параметры датчика:**
- Точность: ±5°C
- Разрешение: 0.5°C
- Диапазон: -40°C до +85°C
- Время отклика: ~1 мс
- Не прерывает потоковую передачу

**Примечание:** На текущем этапе развития возвращается placeholder значение (~28°C). 
Для полной функциональности требуется конфигурация DTS (Digital Temperature Sensor) в STM32CubeMX.
Подробнее: HostTools/TEMP_SENSOR_GUIDE.md

## 4. Статусная структура (предложенный/текущий вид)
Передаётся в виде отдельного короткого bulk IN пакета (<=64 байт). 
Предлагаемое поле `magic='STAT'` (4 ASCII) для идентификации.

```
struct __attribute__((packed)) VendorStatus {
    char     sig[4];            // 'STAT'
    uint8_t  version;           // 1
    uint8_t  reserved0;
    uint16_t cur_samples;       // зафиксированный cur_samples_per_frame (0 если ещё нет)
    uint16_t frame_bytes;       // 32 + 2*cur_samples (0 если нефикс.)
    uint16_t test_frames;       // сколько тестовых кадров отправлено
    uint32_t produced_seq;      // текущий seq (созданных пар)
    uint32_t sent0;             // отправлено ADC0 кадров
    uint32_t sent1;             // отправлено ADC1 кадров
    uint32_t dbg_tx_cplt;       // завершений (USBD_VND_TxCplt)
    uint32_t dbg_partial_frame_abort; // отфильтровано частичных
    uint32_t dbg_size_mismatch; // несовпадений размеров (если считаются)
    uint32_t dma_done0;         // DMA full complete ADC0
    uint32_t dma_done1;         // DMA full complete ADC1
    uint32_t frame_wr_seq;      // внутренняя позиция записи кадра/буфера
    uint16_t flags_runtime;     // runtime флаги state machine
    uint16_t reserved1;
};
```

Хост может парсить по сигнатуре и выводить метрики даже до старта основного потока.

### 4.0.0. Управление ролью RS485 sync (`CMD_SET_SYNC_MODE`, 0x1D)

По умолчанию firmware работает в auto-role: устройства сами выбирают `MASTER`/`SLAVE` по RS485
sync/UID arbitration. Хост может либо разрешить этот самостоятельный выбор, либо принудительно
назначить конкретную роль.

Payload `CMD_SET_SYNC_MODE`:

- `[0x00]` — forced `MASTER`
- `[0x01]` — forced `SLAVE`
- `[0x02]` — forced `OFF`
- `[0x03]` или `[0xFF]` — `AUTO`, снять host-forced и вернуть самостоятельный выбор
- `[0x01, node_id]` — forced `SLAVE` и одновременно задать локальный slave номер, `node_id=1..31`

Номер slave можно менять отдельно командой `CMD_SET_RS485_ID` (`0x3D`), но для фиксированной
топологии рекомендуется атомарный вариант `[0x01, node_id]`, чтобы роль и номер пришли одной
командой. `node_id=0` сбрасывает временный локальный id.

EP0 варианты:

- OUT без data stage: `bRequest=0x1D`, `wValue=mode`. Подходит для `MASTER`/`SLAVE`/`OFF`/`AUTO`,
  но не передает `node_id`.
- OUT с data stage: `bRequest=0x1D`, payload `[mode]` или `[mode,node_id]`. Этот вариант нужен
  для forced `SLAVE` с конкретным номером.

Контроль:

- `LCDS.flags bit4` (`0x0010`) = `host_forced`.
- `EVT1 SYNC_STATE` payload содержит `sync_mode_public` и `sync_mode_host_forced`.
- `GET_STATUS` показывает `sync_local_status`/`sync_status_bytes`; номер slave в публичном
  status byte лежит в bits0..4.

### 4.0.1. Оптический датчик в STAT и RS485 status byte

Состояние локального оптического датчика должно быть доступно хосту в `STAT` и передаваться
соседней антенне в RS485 status byte.

- `flags_runtime bit 0x0020` — локальный оптический датчик активен.
- `flags_runtime bit 0x0080` — master optic активен: локально на master или принят по RS485 на slave.
- `flags_runtime bit 0x0100` — активен любой локальный/RS485 optic в группе.
- `reserved3 bit0` — legacy packed-дубль локального `optic_active`.
- `sync_local_status bit5` (`0x20`) — локальный RS485 status bit оптического датчика.
- `sync_status_bytes[node_id-1] bit5` (`0x20`) — состояние оптического датчика удаленной антенны.

Формат RS485 status byte:

```text
bits 0..4  node_id
bit  5     optic_active, состояние оптического датчика
bit  6     DetADC1
bit  7     DetADC2
```

Исключение на сырой RS485-шине: `master_status0 bits0..4` используются как selector слота опроса slave, а `master_status0 bit5` уже является статусом оптического датчика master. `master_status1` в штатном случае несет `0xC0 | master_id`; firmware на slave использует это как служебную информацию о master, публичные `sync_seen_mask`/`sync_status_bytes` содержат только slave nodes `1..N`. Для host-visible slave status свежий `master_status0 bit5` экспортируется в старом `STAT v5` как `flags_runtime bit0x0080`.

Индикация onboard/system address WS2812:

- Master при локальном `optic_active=1` меняет базовый синий на зеленый.
- Каждый slave показывает свой локальный `optic_active=1` желтым; если локального срабатывания нет, но master сообщил `optic_active=1` через свежий `master_status0 bit5`, slave меняет базовый белый на магента/фиолетовый, пока master status не устареет.
- Этот master bit не добавляет master в `sync_status_bytes`; slave-host читает его через `flags_runtime bit0x0080` в `STAT v5` без увеличения размера `STAT` выше 136 байт.

Внешние эффекты имеют отдельный optic-gate:

- TX200 не gated по оптическим датчикам. В текущей firmware подтверждённое состояние TX при любом состоянии USB следует persistent request `CMD_SET_TX_ENABLE`/`TX200`. `STOP_STREAM`, отсутствие SOF/heartbeat, `HOST_RX_ACK` и `HOST_RX_CLEAR` request не меняют.
- Оптический 38 kHz carrier не gated по приемнику: `SET_OPTIC_POWER=255` задает максимум для проверки фотоприемника.
- `SET_LED_PATTERN` и `LED_EVENT` задают желаемое состояние внешней WS2812-ленты, но лента разрешается только при активном optic-gate.
- Optic-gate активен, если есть локальный `optic_active=1`, свежий `master_status0 bit5=1` на slave или свежий `sync_status_bytes[*] bit5=1` от slave-узла.
- Если все optic bits равны 0 или устарели, внешняя лента рендерится как `OFF`; onboard/system address WS2812 продолжает показывать роль.

COM/UART bench-команды без USB Vendor:

- `TX200 1` / `TX200 0` — вручную задать request TX200. `OPTIC` должен подтвердить соответственно `tx_req=1, tx200=1` или `tx_req=0, tx200=0`; также видны счётчик и значение последней host-команды.
- `OPTP 255` — максимальная мощность 38 kHz carrier.
- `OPTH 0..600` — hold локального `optic_active` в deciseconds (`0` = default).
- `OPTIC` — распечатать `tx200/tx_req/power/hold_ds/rx/pd0/any/master_rx/local_status/master_status/master_flags`; `local_status bit5` (`0x20`) равен локальному `optic_active`.
- `SYNCSTATE` — компактный sync/role status, также содержит `local_status` и `master_status`.

Хост получает состояние двумя способами: по запросу `GET_STATUS` (`0x30`, полный `STAT` 136 байт)
или как событие `STAT` при каждом изменении локального `optic_active`/bit5. При событии устройство
должно отправить `STAT` сразу, если IN endpoint свободен, либо поставить его в очередь до освобождения
endpoint.

### 4.0.2. RS485 identity/IP (`RID1`)

Устройства RS485 могут входить в одну рабочую группу, а могут только быть синхронизированы по
шине. Поэтому кроме runtime status byte есть отдельная медленная таблица identity: короткий
номер устройства и IPv4.

Хост-команды:

- `CMD_SET_RS485_IP` (`0x3E`): payload 4 байта IPv4 в порядке `a.b.c.d`. Firmware не знает IP
  роутера/хоста самостоятельно. Если роутера нет, host должен записать fallback IP хоста.
- `CMD_REQUEST_RS485_IDENT` (`0x3F`): без payload. Отправлять текущему master; master запускает
  один полный проход страниц identity.
- `CMD_GET_RS485_IDENT` (`0x40`): EP0 vendor IN, `wValue=node_id`, `node_id=0` значит локальная
  строка USB-устройства. Длина чтения 32 байта.

Формат ответа `RID1`:

```c
struct __attribute__((packed)) Rs485IdentV1 {
    char     sig[4];          // 'RID1'
    uint8_t  version;         // 1
    uint8_t  node_id;         // 0 если строки нет
    uint16_t flags;           // bit flags ниже, LE
    char     short_id[10];    // 9 hex digits + NUL, '?' если неполно
    uint8_t  ip4[4];          // a.b.c.d
    uint32_t seen_page_mask;  // bit0..bit16
    uint32_t last_ms;         // HAL_GetTick() последнего обновления
    uint16_t reserved;
};
```

Флаги `flags`:

- `0x0001 SHORT_VALID`
- `0x0002 IP_VALID`
- `0x0004 COMPLETE`
- `0x0008 LOCAL`
- `0x0010 RECENT`
- `0x0020 SCAN_ACTIVE`

Raw RS485 exchange не добавляет длинный пакет и не меняет sync cadence:

- После sync всегда идут те же 2 байта master word.
- `master_status0 bits0..4` = адрес/selector запроса: `1..31` slave id, `0` служебный слот master
  без ответа slave. `bits5..7` остаются status-флагами master.
- `master_status1 = 0xC0 | master_id`: штатный master info.
- `master_status1 = 0xA0 | new_id`: compact-assignment для slave, чей адрес указан в
  `master_status0 bits0..4`.
- `master_status1 = 0x80 | page`: identity-запрос страницы `0..16` к slave, чей адрес указан в
  `master_status0 bits0..4`.
- Ответ выбранного slave: первый байт обычный RS485 status byte, второй байт `0x40 | nibble`.
- `page 0..8` = 9 nibble короткого hex-номера от старшего к младшему. `page 9..16` = IPv4 nibble
  в порядке `a.b.c.d`, старшая половина байта затем младшая.
- Невыбранные slave во время identity-запроса не отвечают, но слушают ответ выбранного slave и
  тоже обновляют свою таблицу.

## 4.1. Структура LCD sync-индикатора

Отдаётся отдельным коротким ответом `magic='LCDS'` (24 байта). Запрос рекомендуется слать через EP0 vendor IN, чтобы не вмешиваться в A/B поток.

```
struct __attribute__((packed)) VendorLcdStatus {
    char     sig[4];            // 'LCDS'
    uint8_t  version;           // 1
    uint8_t  raw_mode;          // 0=master, 1=slave, 2=off
    uint8_t  display_mode;      // то, что сейчас рисуется на LCD
    uint8_t  display_value;     // число, которое LCD рисует рядом с M/S
    uint8_t  slave_count;       // сырое rs485_slave_count_estimate
    uint8_t  node_id;           // сырое rs485_local_node_id
    uint8_t  display_color_id;  // 1=RED, 2=GREEN, 5=CYAN, ...
    uint8_t  display_char;      // 'M', 'S' или 'O'
    uint16_t display_rgb565;    // реальный цвет LCD в RGB565
    uint16_t flags;             // bit0 signal_alive, bit1 sync_ok_visual,
                                 // bit2 color_locked, bit3 display_fallback,
                                // bit4 host_forced,
                                // bit5 role_overlay_enabled,
                                // bit6 role_overlay_active
    uint32_t sync_age_ms;       // возраст последнего sync edge; 0xFFFFFFFF если edge не было
    char     text[4];           // готовый префикс LCD: "M03", "S07", "O  "
};
```

Смысл полей:

- `raw_mode` — реальный режим логики sync.
- `display_mode` — режим, который фактически показан на LCD. В обычном маленьком индикаторе при
  потере sync LCD принудительно показывает `M00`; когда активен большой role overlay, поля
  `display_*` показывают raw-роль (`Mxx`/`Sxx`) без этого fallback.
- `display_value` — для `MASTER` это число обнаруженных slave, для `SLAVE` это локальный slot/node id.
- `display_color_id` / `display_rgb565` — цвет индикатора на LCD.
- `flags.display_fallback=1` — LCD сейчас показывает аварийный fallback (`M00`, цвет `CYAN`).
- `flags.signal_alive=1` — LCD считает sync "живым".
- `flags.sync_ok_visual=1` — LCD считает sync "хорошим"; после антидребезга цвет становится `GREEN`.
- `flags.color_locked=1` — зелёный уже защёлкнут внутренним state machine LCD.
- `flags.role_overlay_enabled=1` — host разрешил крупный периодический overlay роли.
- `flags.role_overlay_active=1` — на LCD сейчас показан крупный `Mxx`/`Sxx`; в этом состоянии
  `display_rgb565` и `display_color_id` относятся к цвету большого текста.

### 4.1.1. Крупная LCD-индикация роли (`CMD_SET_LCD_ROLE_OVERLAY`, 0x41)

Команда не меняет RS485 sync и не добавляет данных в sync-пакет. Она только управляет локальным
LCD overlay, который отрисовывается из основного цикла с низким приоритетом.

Payload:

- `[0x00]` — запретить overlay и вернуть обычный LCD screen.
- `[0x01]` — разрешить overlay с текущими/дефолтными временами.
- `[enable, period_s, duration_s]` — задать интервал между показами и длительность показа.
  `period_s` и `duration_s` ограничиваются диапазоном `3..5`, дефолт `4/4`.

Формат на LCD:

- `Mxx` — устройство в роли `MASTER`, `xx` = число активных slave из RS485 status table.
- `Sxx` — устройство в роли `SLAVE`, `xx` = локальный `node_id`.
- `O  ` — sync выключен.

Цвет большого текста выбирается случайно из ярких цветов `RED/GREEN/YELLOW/BLUE/CYAN/WHITE`.
EP0 OUT без data stage поддерживает `bRequest=0x41`, младший байт `wValue` = `enable`.
Для задания `period_s/duration_s` используйте bulk OUT или EP0 OUT с data stage.

## 5. Тестовый кадр
Отправляется сразу после `CMD_START_STREAM`.  
Флаги: 0x81 (бит7 TEST + бит0 ADC0).  
`total_samples=8`, фиксированные/диагностические данные.  
Не влияет на фиксацию рабочего размера кадра.

## 6. CRC16 (опционально)
Алгоритм: CRC16-CCITT-FALSE (poly=0x1021, init=0xFFFF, без рефлексии).  
Порядок вычисления: сначала 30 байт заголовка (без поля crc16), затем payload.  
При несоответствии — хост увеличивает `crc_bad` и может сбрасывать поток/запрашивать STOP.

## 7. Инварианты, которые проверяет хост
1. Все рабочие кадры (не TEST) имеют одинаковый `total_samples = exp_samples`.
2. `exp_frame_size` фиксируется по первому рабочему кадру и не меняется.
3. Для каждого `seq` присутствуют либо оба кадра (0x01 и 0x02), либо (во время запуска) временно один; дубликаты запрещены.
4. Нет коротких IN transfers кроме тестового кадра или статусных пакетов <=64B.
5. `crc_bad == 0` при включенном флаге CRC.
6. Без пропусков последовательности (`seq_gaps == 0`) и без откатов.

## 8. Отладочные счётчики прошивки (минимум)
- `produced_seq` — сколько пар сформировано (инкремент после отправки обеих ADC).
- `sent0/sent1` — фактическое кол-во отправленных кадров по каждому ADC.
- `dbg_tx_cplt` — число завершений передачи на уровне USB.
- `dbg_partial_frame_abort` — игнорированных кадров из-за несоответствия размера до фиксации.
- `dbg_size_mismatch` — кадров с неверной длиной (если включено).
- `dma_done0/dma_done1` — завершения DMA.
- `frame_wr_seq` — индекс производственного кольца.

## 8.1. CMD_GET_TEMP (0x31) — Получить температуру кристалла
Читает встроенный температурный датчик STM32H723.

**Request (OUT)**: 1 байт `0x31` (no payload)
**Response (IN)**: 4 байта
- Byte 0: `0x80` (RSP_ACK)
- Byte 1: `0x31` (echo command)
- Bytes 2-3: температура в °C (int16_t, LE)

**Пример**: ответ `[0x80, 0x31, 0x1C, 0x00]` = `+28°C`.

**Заметки**:
- Диапазон: -40°C до +85°C
- Точность: ±5°C (встроенная калибровка датчика)
- Разрешение: 0.5°C
- Время отклика датчика: ~1 ms
- Команда может быть отправлена в любой момент (в режиме потока или ожидания)

## 8.2. CMD_GET_VERSION (0x32) — Получить версию прошивки
Возвращает версию встроенного ПО в формате `MAJOR.MINOR.PATCH`.

**Request (OUT)**: 1 байт `0x32` (no payload)
**Response (IN)**: 6 байт
- Byte 0: `0x80` (RSP_ACK)
- Byte 1: `0x32` (echo command)
- Byte 2: major версия (u8)
- Byte 3: minor версия (u8)
- Byte 4: patch версия (u8)
- Byte 5: build число (u8, зарезервировано, обычно 0)

**Пример**: ответ `[0x80, 0x32, 0x01, 0x02, 0x03, 0x00]` = версия `1.2.3`.

**Заметки**:
- Семантическое управление версионированием (semantic versioning)
- Build число — зарезервировано для будущего использования
- Команда не имеет побочных эффектов и может быть отправлена в любой момент
- Полезна для проверки совместимости хоста и прошивки

## 9. Типичные проблемы и их сигнатуры
| Симптом (хост)                        | Возможная причина прошивки                      |
|--------------------------------------|-------------------------------------------------|
| Только тестовый кадр, далее тишина   | Не стартует DMA / не фиксируется размер         |
| `magic_bad` растёт                   | Перезапись буфера до полной готовности / мусор  |
| `transfer_len_min < transfer_len_max`| Смешаны разные `total_samples`                   |
| `gaps` > 0 при `dup_seq` растущем    | Повторная отправка завершённых seq              |
| Нет статусного ответа                | Статус шлётся на другой endpoint или не формируется |

## 10. Примечания по ROI
CMD_SET_ROI_US: параметр — номер стартового семпла (0..N-1). Прошивка использует длину 200
и сдвигает окно ROI на указанный старт. Если старт выходит за пределы, он ограничивается
в диапазоне 0..(samples-200). Это относится к режимам LOSSLESS_ROI и AVG_ROI.

## 10.1. Настраиваемая скорость DC-компенсации

DC-компенсация обучается в трёх режимах плавным slew-rate алгоритмом.
Хост задаёт не фиксированный шаг и не число кадров, а время ухода максимальной ошибки
32768 LSB к virtual zero/deadband в миллисекундах. Чем меньше `*_settle_ms`, тем больше
допустимый шаг на новом ADC-кадре. Фиксированной частоты адаптации нет: частота кадров
только даёт моменты обновления, а скорость задаёт `settle_ms`.
Режимы работают постоянно до следующей команды хоста; меняется только скорость адаптации.
Веб-интерфейс может показывать те же значения в секундах.

Режимы:

- `0=FREEZE/Stop` — DC вычитается, но новые значения не обучаются.
- `1=WORK` — рабочая медленная подстройка постоянных изменений DC.
- `2=DETECT` — средняя скорость для периода детекции метки.
- `3=BOOT_FAST/Acquisition` — ускоренная подстройка, остаётся активной до следующей команды хоста.

Дефолты прошивки/хоста: `WORK=5 s`, `BOOT_FAST/Acquisition=500 s`, `DETECT=10000 s`, `FREEZE/Stop=0 s`.

`CMD_SET_DC_CONFIG` (`0x1F`) payload после opcode. `version=1` оставлен для совместимости
и включает старое поведение: DC применяется/обучается до усреднения, post-stage выключен.

```
struct DcConfigSetV1 {
    uint8_t  version;          // 1
    uint8_t  mode;             // 0=FREEZE/Stop, 1=WORK, 2=DETECT, 3=BOOT_FAST/Acquisition
    uint16_t flags;            // сейчас 0, зарезервировано
    uint32_t work_settle_ms;   // default 5000 (5 s), минимум 1 ms
    uint32_t detect_settle_ms; // default 10000000 (10000 s), минимум 1 ms
    uint32_t fast_settle_ms;   // default 500000 (500 s Acquisition), минимум 1 ms
    uint32_t adapt_settle_ms;  // legacy wire-name fast_duration_ms; скорость выбранного режима, не таймер
};
```

Новый payload `version=2` позволяет выбирать, где делать DC для `AVG_ROI`, и задавать
скорость pre/post отдельно:

```
struct DcConfigSetV2 {
    uint8_t  version;          // 2
    uint8_t  mode;             // 0=FREEZE/Stop, 1=WORK, 2=DETECT, 3=BOOT_FAST/Acquisition
    uint16_t flags;            // stage flags ниже
    uint32_t work_settle_ms;   // base WORK speed, минимум 1 ms
    uint32_t detect_settle_ms; // base DETECT speed, минимум 1 ms
    uint32_t fast_settle_ms;   // base BOOT_FAST speed, минимум 1 ms
    uint32_t pre_settle_ms;    // pre-average override; 0 = use mode speed
    uint32_t post_settle_ms;   // post-average override; 0 = use mode speed
};
```

Stage flags:

- `0x0010 PRE_APPLY`
- `0x0020 PRE_LEARN`  (также включает apply)
- `0x0040 POST_APPLY`
- `0x0080 POST_LEARN` (также включает apply)

Если все stage flags равны 0, firmware применяет совместимый default `PRE_APPLY|PRE_LEARN`.
Для pre и post используется одна общая таблица коэффициентов `[channel][parity][sample]`.
Одновременно применять её в обеих точках нельзя, иначе компенсация удвоится. Поэтому firmware
нормализует комбинации к одной эффективной стадии с приоритетом
`POST_LEARN > PRE_LEARN > POST_APPLY > PRE_APPLY`; `GET_DC_CONFIG` возвращает эффективные флаги.
Переключение стадии не очищает таблицу и не должно вызывать повторного появления DC.
`LOSSLESS_ROI` использует только pre-stage. В `AVG_ROI` pre-stage обрабатывает raw ROI до суммы,
post-stage обрабатывает уже усредненный ROI перед отправкой по USB.

`CMD_GET_DC_CONFIG` (`0x3A`) рекомендуется читать через EP0 vendor IN, чтобы не вмешиваться
в поток A/B. Ответ `DCCF`:

```
struct DcConfigStatusV1 {
    char     sig[4];           // 'DCCF'
    uint8_t  version;          // 1
    uint8_t  mode;             // текущий/effective режим
    uint16_t flags;            // bit0 adapt_enabled, bit1 auto_freeze, bit2 dirty,
                               // bit4 pre_apply, bit5 pre_learn, bit6 post_apply, bit7 post_learn
    uint32_t work_settle_ms;
    uint32_t detect_settle_ms;
    uint32_t fast_settle_ms;
    uint32_t fast_duration_ms; // legacy wire-name; v2 reports pre_settle_ms override
    uint32_t active_settle_ms; // settle выбранной эффективной стадии pre/post
    uint32_t mode_enter_ms;    // HAL_GetTick() входа в режим
    uint32_t fast_until_ms;    // legacy wire-name; v2 reports post_settle_ms override
    uint32_t adapt_updates;    // счётчик принятых обновлений DC
};
```

Legacy команды сохранены:

- `CMD_SET_DC_ADAPT 0` теперь эквивалентен `mode=FREEZE`.
- `CMD_SET_DC_ADAPT 1` теперь эквивалентен `mode=WORK`.
- `CMD_CALIB_DC_FAST 0x1E`: ненулевой legacy-параметр выбирает `BOOT_FAST`, ноль выбирает `WORK`; режим действует до следующей DC-команды.

## 11. Roadmap (расширения)
- Динамическая смена размера кадра через новую команду (например 0x31) с подтверждением.
- Включение CRC по отдельной команде (0x32) + бит флага.
- Введение зон (zone_count >0) для сегментации payload.
- Метка точного времени (timestamp 64‑бит) в версии 2 заголовка.

## 12. Требования к обратной совместимости
Изменение структуры `VendorHdr` требует:
1. Инкрементировать `version`.
2. Не изменять первые 12 байт (magic, version, flags, seq) — хост полагается на них.
3. Добавлять новые поля только в хвост либо через `zone` блоки.

## 13. Минимальный алгоритм хоста (C)
1. Открыть устройство, определить ep_in/ep_out.
2. Поставить очередь IN transfers.
3. Отправить SET_* команды.
4. Отправить START_STREAM.
5. Игнорировать тестовый кадр (flags & 0x80).
6. Первый рабочий кадр фиксирует `exp_frame_size`/`exp_samples`.
7. Собираем пары по (seq, flags).
8. По завершении — STOP_STREAM → прочитать статус.

## 14. Диагностический чеклист при регрессии
1. Есть ли тестовый кадр? Если нет — проблема в пути USB передачи.
2. Растут ли dma_doneX? Если нет — ADC/DMA не стартует.
3. Фиксировался ли cur_samples_per_frame? Если 0 — нет первого полного кадра.
4. Есть ли расхождение sent0 != sent1? Если да — один ADC не даёт буфер.
5. Есть дубликаты seq? Если да — повторная отправка того же буфера.
