# USB VENDOR ПРОТОКОЛ (версия 1.0)
 
Документ фиксирует формат кадров, команды управления и инварианты хоста/прошивки. 
Цель — исключить регрессии и «забывание» деталей при дальнейших изменениях.

## 1. Идентификация устройства
VID: 0xCAFE  
PID: 0x4001  
Composite: CDC + Vendor (интерфейс vendor обычно №2).  
Bulk endpoints (alt0):
- OUT: 0x03 (host → device, команды)
- IN : 0x83 (device → host, поток и статус / тестовый кадр)

## 2. Формат потокового кадра
Каждый кадр = 32‑байтовый заголовок `VendorHdr` + payload (сырые сэмплы) + (опц.) CRC16.

```
Offset Size  Field            Type      Описание
0      2     magic            u16       0xA55A (LE)
2      1     version          u8        Текущая версия структуры (1)
3      1     flags            u8        Биты, см. ниже
4      4     seq              u32       Номер логической последовательности (кадровая пара)
8      4     timestamp        u32       Временная метка (мс или device ticks*)
12     2     total_samples    u16       Кол-во сэмплов в payload (для данного ADC кадра)
14     2     zone_count       u16       Зарезервировано (0)
16     4     zone1_offset     u32       Зарезервировано (0)
20     4     zone1_length     u32       Зарезервировано (0)
24     4     reserved         u32       (0)
28     2     reserved2        u16       (0)
30     2     crc16            u16       CRC16-CCITT-FALSE заголовок+payload (при флаге CRC)
```
Endian: Little‑endian для всех многобайтовых полей.

Payload: массив `total_samples` значений по 2 байта (LE). (Т.е. размер payload = `2 * total_samples`).  
Флаг CRC (bit2) определяет присутствие и валидацию crc16. Если бит не установлен — поле crc16 может быть 0 (игнорируется).

### 2.1 Флаги `flags`
| Бит | Маска | Значение                    |
|-----|-------|----------------------------|
| 0   | 0x01  | Кадр ADC0                  |
| 1   | 0x02  | Кадр ADC1                  |
| 2   | 0x04  | CRC включён                |
| 7   | 0x80  | Тестовый кадровый маркер   |

Комбинации: рабочие кадры используют ровно один из {0x01,0x02} (+ возможно 0x04). Тестовый кадр: 0x81 (ADC0 + TEST).  
Флаги 0x01 и 0x02 одного и того же `seq` образуют стерео‑пару. 

### 2.2 Последовательность и пары
`seq` инкрементируется после успешной отправки двух кадров (ADC0 и ADC1) для данной последовательности.  
Инвариант: для любого `seq` должно быть не более по одному кадру с флагом 0x01 и по одному с 0x02. Дубликаты запрещены.  
Хост проверяет: монотонность seq без дыр; приём пары -> счётчик стерео‑пар.

### 2.3 Фиксация размера (auto‑lock)
Алгоритм прошивки:
1. `cur_samples_per_frame` = 0 при старте.
2. Первый полный DMA кадр (или отдельный механизм) фиксирует значение `cur_samples_per_frame` и 
вычисляет `cur_expected_frame_size = 32 + 2*cur_samples_per_frame`.
3. Все следующие кадры должны иметь ровно `total_samples == cur_samples_per_frame`. 
Иначе — игнорируются (`dbg_partial_frame_abort++`).

Допустимые рабочие размеры на сегодня: 912 / 944 / 976 (примерные варианты).  
Тестовый кадр (8 сэмплов) НЕ фиксирует рабочий размер; хост игнорирует его при установке `exp_frame_size`.

## 3. Команды управления (bulk OUT на EP 0x03)
Каждая команда: первый байт = код, далее опциональный payload (не более 63 байт). 
Ответ (если предусмотрен) приходит как отдельный bulk IN пакет 
(может быть статусным коротким кадром или стандартным кадром, в зависимости от реализации).

| Код  | Имя             | Назначение | Payload OUT | Ответ IN |
|------|-----------------|------------|-------------|----------|
|0x14  | CMD_SET_PROFILE | Выбор профиля обработки/фильтра | 1 байт profile | (опц.) статус*
|0x13  | CMD_SET_FULL_MODE| 0=ROI, 1=FULL режим захвата    | 1 байт flag    | (опц.) статус*
|0x15  | CMD_SET_ROI_US  | Задание ROI по номеру семпла   | 4 байта (u32)  | (опц.) статус*
|0x1D  | CMD_SET_SYNC_MODE | Сохраняемая локальная роль master/slave / временный OFF/AUTO | MASTER/SLAVE: `mode + u64 unix_ms LE`; OFF/AUTO: 1 байт mode | нет
|0x1F  | CMD_SET_DC_SPEED | Единственная скорость DC-компенсации | `uint32_t settle_ms` LE; 0=off, 1=fastest, 1000=1s | нет
|0x20  | CMD_START_STREAM| Запуск потока: отправить тестовый кадр + начать фиксацию размера | none | поток
|0x21  | CMD_STOP_STREAM | Остановка: прекращение потока, сброс внутренних флагов | none | статусная структура
|0x30  | CMD_GET_STATUS  | (Расширенный) запрос статуса     | none | статусная структура
|0x31  | CMD_GET_TEMP    | Получить температуру кристалла  | none | RSP_ACK + cmd + 2 байта (int16_t LE)
|0x32  | CMD_GET_VERSION | Получить версию прошивки        | none | RSP_ACK + cmd + 4 байта (major, minor, patch, build)
|0x33  | CMD_SET_TX_ENABLE | Persistent host-request TX200: 1 включает передачу, 0 выключает | 1 байт: 0/1 | (опц.) статус*
|0x38  | CMD_GET_LCD_STATUS | Снимок sync-индикатора LCD (`M/S/O`, число, цвет) | none | структура `LCDS` (24 байта)
|0x3A  | CMD_GET_DC_CONFIG | Снимок текущих настроек DC-компенсации | none | структура `DCCF` (40 байт)
|0x3D  | CMD_SET_RS485_ID | Постоянный локальный device_id, независимый от роли | 1 байт: 0..31 | нет
|0x3E  | CMD_SET_RS485_IP | Локальный IPv4 для RS485 identity | 4 байта: `a,b,c,d` | нет
|0x3F  | CMD_REQUEST_RS485_IDENT | Запустить один master-scan ID/IP по RS485 | none | нет
|0x40  | CMD_GET_RS485_IDENT | Получить строку таблицы RS485 identity | EP0 IN: `wValue=0..31` device, `0xFF` local | структура `RID1` (32 байта)
|0x41  | CMD_SET_LCD_ROLE_OVERLAY | Разрешить/запретить крупную LCD-индикацию роли | `enable`, опц. `period_s,duration_s` | нет
|0x42  | CMD_SET_RPI_INFO | Сообщить локальные номер RPI и IPv4 | `u16 rpi_number LE + ip[4]` | нет
|0x43  | CMD_GET_RS485_SENSOR | Получить 16 срочных sensor bits узла | EP0 IN: `wValue=0..31`, `0xFF` local | `SNS1` (16 байт)

`*` Статус после SET_* может быть отложен или не возвращаться — зависит от реализации.
Гарантированно возвращается после STOP и GET_STATUS.

## 3.1. Команда GET_TEMP (0x31) - Получение температуры

Команда 0x31 возвращает текущую температуру кристалла встроенного датчика STM32H723.

**Запрос (OUT → 0x03):**
- Один байт: `0x31`
- Без payload

**Ответ (IN ← 0x83):**
- 4 байта:
    - Byte 0: `0x80` (RSP_ACK)
    - Byte 1: `0x31` (echo команды)
    - Bytes 2-3: температура кристалла (int16_t, LE)

**Примеры:**
- `+28°C`: ответ `[0x80, 0x31, 0x1C, 0x00]` → 0x001C = 28
- `-10°C`: ответ `[0x80, 0x31, 0xF6, 0xFF]` → 0xFFF6 = -10 (дополнительный код)

**Параметры датчика:**
- Точность: ±5°C
- Разрешение: 0.5°C
- Диапазон: -40°C до +85°C
- Время отклика: ~1 мс
- Не прерывает потоковую передачу

**Примечание:** На текущем этапе развития возвращается placeholder значение (~28°C). 
Для полной функциональности требуется конфигурация DTS (Digital Temperature Sensor) в STM32CubeMX.
Подробнее: HostTools/TEMP_SENSOR_GUIDE.md

## 4. Статусная структура (предложенный/текущий вид)
Передаётся отдельным bulk IN пакетом: 64/96/136 байт для совместимых версий
или 137 байт для прямой карты ID 0..31.
Предлагаемое поле `magic='STAT'` (4 ASCII) для идентификации.

```
struct __attribute__((packed)) VendorStatus {
    char     sig[4];            // 'STAT'
    uint8_t  version;           // 1
    uint8_t  reserved0;
    uint16_t cur_samples;       // зафиксированный cur_samples_per_frame (0 если ещё нет)
    uint16_t frame_bytes;       // 32 + 2*cur_samples (0 если нефикс.)
    uint16_t test_frames;       // сколько тестовых кадров отправлено
    uint32_t produced_seq;      // текущий seq (созданных пар)
    uint32_t sent0;             // отправлено ADC0 кадров
    uint32_t sent1;             // отправлено ADC1 кадров
    uint32_t dbg_tx_cplt;       // завершений (USBD_VND_TxCplt)
    uint32_t dbg_partial_frame_abort; // отфильтровано частичных
    uint32_t dbg_size_mismatch; // несовпадений размеров (если считаются)
    uint32_t dma_done0;         // DMA full complete ADC0
    uint32_t dma_done1;         // DMA full complete ADC1
    uint32_t frame_wr_seq;      // внутренняя позиция записи кадра/буфера
    uint16_t flags_runtime;     // runtime флаги state machine
    uint16_t reserved1;
};
```

Хост может парсить по сигнатуре и выводить метрики даже до старта основного потока.

### 4.0.0. Управление ролью RS485 sync (`CMD_SET_SYNC_MODE`, 0x1D)

Автоматического голосования за `MASTER` нет. Если сохранённого назначения ещё нет, все устройства
остаются пассивными `SLAVE`, пока RPI не назначит master.

Роль — локальная настройка конкретной платы. `MASTER` или `SLAVE`, выбранные её RPI, немедленно
сохраняются во Flash и восстанавливаются после reset/power-cycle. Назначение не распространяется
на соседние платы и чужие UID/role/enum кадры не могут его изменить. Поэтому несколько ошибочно
назначенных master остаются видимыми, пока пользователь/RPI явно не переведёт лишние платы в
`SLAVE`.

Смена или повторное подтверждение роли не очищает установленную RPI частоту буферов, не
перезапускает ADC/DMA, не сбрасывает ADC frame/parity sequence и не меняет состояние `TX200`,
заданное последней командой `SET_TX_ENABLE`.

Payload `CMD_SET_SYNC_MODE`:

- `[0x00, unix_ms_u64_le]` — сохранить локальную роль `MASTER`; всего 9 байт payload
- `[0x01, unix_ms_u64_le]` — сохранить локальную роль `SLAVE`; всего 9 байт payload
- `[0x02]` — forced `OFF`
- `[0x03]` или `[0xFF]` — снять временный `host_forced` и вернуться к сохранённой роли

`unix_ms` — UTC Unix time в миллисекундах, little-endian; поле сохранено для совместимости.
Команда RPI является авторитетной и принимается с первого раза.

`CMD_SET_RS485_ID (0x3D)` отдельно задаёт постоянный `device_id` в диапазоне `0..31`.
Команда разрешена в обеих ролях. ID сохраняется во Flash, не меняется вместе с ролью и не
перенумеровывается при изменении состава группы. Неназначенность хранится отдельным флагом:
назначенный ID 0 отображается как M00/S00. Назначение идёт только по локальному USB своего RPI;
неназначенная плата молчит в RS485, но ADC и USB продолжают работать.

Специального selected sensor-slave больше нет. Состояния `optic/DetADC1/DetADC2` каждого
устройства адресуются как `sync_status_bytes[device_id]`, включая master.
Изменения sensor bits передаются приоритетно в ближайшем цикле 200 Hz и повторяются трижды;
фоновая identity-карта всегда уступает им.
На USB при каждом таком изменении ставятся `EVT1 type=0x14 SENSOR_MAP` с прямой
32-элементной картой и совместимый 136-байтовый `STAT v5`. В `STAT v5` index/bit
`0..30` означает старые `device_id 1..31`; прямой `device_id 0` доступен в `STAT v6`.

EP0 варианты:

- OUT без data stage: `bRequest=0x1D`, `wValue=mode`. Подходит только для `OFF`/`AUTO`.
  `MASTER` и `SLAVE` без timestamp возвращают STALL.
- OUT с data stage: для назначения master/slave обязательно передать 9 байт
  `[mode, unix_ms_u64_le]`; для `OFF`/`AUTO` достаточно `[mode]`.

Контроль:

- `LCDS.flags bit4` (`0x0010`) = `host_forced`.
- `LCDS.raw_mode` и `LCDS.node_id` дают роль/ID даже без sync; flags bit7=role persisted,
  bit8=ID conflict, bit9=multiple master, bit10=persisted master.
- `EVT1 SYNC_STATE` содержит те же роль/ID и flags bit5/bit6/bit7.
- `GET_STATUS.flags_runtime`: `0x1000=role persisted`, `0x2000=any ID conflict`,
  `0x4000=multiple master`, `0x8000=persisted role is master`
  (`0x1000` без `0x8000` = persisted slave).

### 4.0.1. Оптический датчик в STAT и RS485 status byte

Единый обработанный сигнал локального оптического датчика `optic_active` должен быть
доступен хосту в `STAT` и передаваться соседним устройствам в RS485 status byte.

- `flags_runtime bit 0x0020` — локальный удержанный `optic_active`.
- `flags_runtime bit 0x0080` — master optic активен: локально на master или принят по RS485 на slave.
- `flags_runtime bit 0x0100` — активен любой локальный/RS485 optic в группе.
- `flags_runtime bits 0x0200/0x0400/0x0800` — legacy selected-slave flags, не используются.
- `reserved3 bit0` — legacy packed-дубль локального `optic_active`.
- `sync_local_status bit5` (`0x20`) — локальный `optic_active`.
- `sync_status_bytes[device_id] bit5` (`0x20`) — переданный `optic_active` удаленного устройства.

Формат RS485 status byte:

```text
bits 0..4  node_id
bit  5     optic_active, обработанный вход с удержанием после HIGH
bit  6     DetADC1
bit  7     DetADC2
```

Исключение на сырой RS485-шине: `master_status0 bits0..4` используются как selector слота опроса slave, а `master_status0 bit5` уже является статусом оптического датчика master. `master_status1` в штатном случае несет `0xC0 | master_id`; firmware на slave добавляет свежий статус master в публичные `sync_seen_mask`/`sync_status_bytes` по его постоянному ID. Для совместимости master optic также экспортируется как `flags_runtime bit0x0080`.

Индикация onboard/system address WS2812:

- Если актуальной RS485-связи нет (`sync_signal_alive=0`), устройство любой
  назначенной роли показывает единый голубой цвет. Сохранённая роль сама по себе
  не считается подтверждением связи.
- При живой связи master имеет базовый синий цвет, slave — базовый белый.
- Master при локальном `optic_active=1` меняет базовый синий на зеленый.
- Каждый slave показывает свой локальный `optic_active=1` желтым; если локальный `optic_active=0`, но master сообщил `optic_active=1` через свежий `master_status0 bit5`, slave меняет базовый белый на магента/фиолетовый, пока master status не устареет.
- Локальный `optic_active=1` имеет высший приоритет над ролью и диагностической ошибкой
  и немедленно меняет только цвет системного LED. Если TX включен, независимая
  модуляция яркости TX-breathe продолжается весь интервал `optic_active=1`.
- Свежий master status добавляется в `sync_status_bytes[master_device_id]`; для совместимости
  master optic также доступен как `flags_runtime bit0x0080`.

Внешние эффекты имеют отдельный optic-gate:

- TX200 не gated по оптическим датчикам. Действует `physical_tx = tx_request AND streaming`: `STOP_STREAM` гасит физические выходы без стирания request, а следующий START восстанавливает их. Краткие пропуски SOF/heartbeat, `HOST_RX_ACK` и `HOST_RX_CLEAR` не дёргают TX и не меняют request.
- Оптический 38 kHz carrier не gated по приемнику: `SET_OPTIC_POWER=255` задает максимум для проверки фотоприемника.
- `SET_LED_PATTERN` и `LED_EVENT` задают желаемое состояние внешней WS2812-ленты, но лента разрешается только при активном optic-gate.
- Optic-gate активен, если есть локальный `optic_active=1`, свежий `master_status0 bit5=1` на slave или свежий `sync_status_bytes[*] bit5=1` от slave-узла.
- Если все optic bits равны 0 или устарели, внешняя лента рендерится как `OFF`; onboard/system address WS2812 продолжает показывать роль.

COM/UART bench-команды без USB Vendor:

- `VER` / `VERSION` — вернуть одну строку
  `VERSION fw=<semver> git=<hash> build_date=<YYYY-MM-DD> build_time=<HH:MM:SS> pairs=<N>`.
  Ответ передаётся напрямую в UART и не зависит от включения подробного отладочного `printf`.
- `TX200 1` / `TX200 0` — вручную задать request TX200. `OPTIC` должен подтвердить соответственно `tx_req=1, tx200=1` или `tx_req=0, tx200=0`; также видны счётчик и значение последней host-команды.
- `OPTP 255` — максимальная мощность 38 kHz carrier.
- `OPTH 0..600` — удержание публичного `optic_active=1` после последней принятой `1`
  в deciseconds (`0` = default).
- `OPTIC` — распечатать `tx200/tx_req/power/hold_ds/rx/activity_hold/pd0/any/master_rx/local_status/master_status/master_flags`; `pd0` — сырой вход, `rx`, `activity_hold` и `local_status bit5` (`0x20`) — единый удержанный `optic_active`.
- `SYNCSTATE` — компактный sync/role status, также содержит `local_status` и `master_status`.

Хост получает состояние двумя способами: по запросу `GET_STATUS` (`0x30`, полный `STAT` v6 137 байт)
или как событие `STAT` при каждом изменении обработанного `optic_active`/bit5.
Переход `0->1` создаётся немедленно по HIGH, переход `1->0` — после истечения hold;
оба также создают `EVT1 SENSOR_MAP`. При событии устройство
должно отправить `STAT` сразу, если IN endpoint свободен, либо поставить его в очередь до освобождения
endpoint.

### 4.0.2. RS485 identity/IP (`RID1`)

Устройства RS485 могут входить в одну рабочую группу, а могут только быть синхронизированы по
шине. Поэтому кроме приоритетного runtime status byte есть общая таблица:
`device_id 0..31 -> UID STM32 + номер RPI + IPv4`.

Хост-команды:

- `CMD_SET_RS485_IP` (`0x3E`): payload 4 байта IPv4 в порядке `a.b.c.d`. Firmware не знает IP
  RPI самостоятельно. Каждый RPI отправляет своей STM32 актуальный адрес после загрузки и при
  каждом изменении адреса. Если роутера нет, RPI записывает свой fallback IP.
- `CMD_REQUEST_RS485_IDENT` (`0x3F`): без payload. На master немедленно перезапускает полный
  проход; на slave безопасно не передаёт отдельный RS485-кадр, потому что карта и так постоянно
  реплицируется автоматическими проходами master.
- `CMD_SET_RPI_INFO` (`0x42`): payload `u16 rpi_number LE + ip[4]`.
- `CMD_GET_RS485_IDENT` (`0x40`): EP0 vendor IN, `wValue=0..31` выбирает `device_id`,
  `wValue=0xFF` означает локальную плату. Длина чтения 32 байта.

Master автоматически запускает новый проход через 5 секунд после предыдущего. Он передаёт
собственные страницы и опрашивает каждый `device_id`; master и все слушающие slave сохраняют каждый
услышанный ответ. Поэтому одинаковую карту можно читать через USB любой платы
группы. RPI обычно читает `sync_seen_mask`, затем `RID1` для соответствующих `0..31`; готовый
вариант — `HostTools/vendor_rs485_device_list.py`.

`sync_seen_mask` является картой реально подключённых устройств: удалённый узел исчезает из неё
через 1000 ms без status-кадров. `RID1` — более медленный фоновый кэш UID/RPI/IP. Если строка
удалённого узла не обновлялась 30 секунд, firmware полностью очищает её: сбрасываются
`seen_page_mask`, `last_ms`, UID/RPI/IP и все флаги назначения/валидности. Локальная строка платы
не стареет. Хост должен скрывать устройство сразу после исчезновения его бита из
`sync_seen_mask`, не дожидаясь очистки `RID1`.

Новый удалённый ID попадает в живую карту только после трёх корректных двухбайтовых ответов в
адресованном ему окне master за интервал не более 500 ms. Один шумовой/повреждённый пакет не
создаёт устройство. После подтверждения обычные status и срочные sensor-event обновляют уже
живой узел немедленно. Чтение `RID1` для удалённого ID выдаёт UID/RPI/IP и флаги назначения только
пока этот ID присутствует в живой карте; 30-секундный кэш наружу как подключённое устройство не
показывается.

Формат ответа `RID1`:

```c
struct __attribute__((packed)) Rs485IdentV1 {
    char     sig[4];          // 'RID1'
    uint8_t  version;         // 1
    uint8_t  node_id;         // device_id 0..31; assignment is a flag
    uint16_t flags;           // bit flags ниже, LE
    char     short_id[10];    // 9 hex digits + NUL, '?' если неполно
    uint8_t  ip4[4];          // a.b.c.d
    uint32_t seen_page_mask;  // bit0..bit20
    uint32_t last_ms;         // HAL_GetTick() последнего обновления
    uint16_t rpi_number;
};
```

Флаги `flags`:

- `0x0001 SHORT_VALID`
- `0x0002 IP_VALID`
- `0x0004 COMPLETE`
- `0x0008 LOCAL`
- `0x0010 RECENT`
- `0x0020 SCAN_ACTIVE`
- `0x0040 SELECTED_SLAVE` (legacy, в новой топологии не используется)
- `0x0080 MASTER`
- `0x0100 NODE_CONFLICT`

Raw RS485 exchange не добавляет длинный пакет и не меняет sync cadence:

- После sync всегда идут те же 2 байта master word.
- `master_status0 bits0..4` = адрес/selector запроса: `1..31` slave id, `0` служебный слот master
  без ответа slave. `bits5..7` остаются status-флагами master.
- `master_status1 = 0xC0 | master_id`: штатный master info.
- `master_status1 = 0xA0 | new_id`: legacy compact-assignment; новая прошивка игнорирует.
- `master_status1 = 0x80 | page`: identity-запрос страницы `0..16` к slave, чей адрес указан в
  `master_status0 bits0..4`.
- Ответ выбранного slave: первый байт обычный RS485 status byte, второй байт `0x40 | nibble`.
- `page 0..8` = 9 nibble короткого hex-номера от старшего к младшему. `page 9..16` = IPv4 nibble
  в порядке `a.b.c.d`, старшая половина байта затем младшая.
- Невыбранные slave во время identity-запроса не отвечают, но слушают ответ выбранного slave и
  тоже обновляют свою таблицу.
- Собственная identity master передаётся парой служебных слов с selector `0`; все slave сохраняют
  её по постоянному номеру RPI master в диапазоне `1..31` и дополнительно в legacy alias `32`.
- Изменение `optic/DetADC1/DetADC2` имеет приоритет над identity. Slave передаёт слово события
  (`status0` с номером RPI и актуальными sensor bits, `status1=0x20|sequence`) в ближайшем
  200 Hz цикле, то есть первая попытка начинается не позднее 5 ms. Событие повторяется трижды;
  обычный выбранный ответ идёт после короткого event-окна. Все устройства обновляют sensor-карту
  сразу по событию. Пропущенная из-за события identity-страница восстанавливается следующим
  автоматическим проходом.

## 4.1. Структура LCD sync-индикатора

Отдаётся отдельным коротким ответом `magic='LCDS'` (24 байта). Запрос рекомендуется слать через EP0 vendor IN, чтобы не вмешиваться в A/B поток.

```
struct __attribute__((packed)) VendorLcdStatus {
    char     sig[4];            // 'LCDS'
    uint8_t  version;           // 1
    uint8_t  raw_mode;          // 0=master, 1=slave, 2=off
    uint8_t  display_mode;      // то, что сейчас рисуется на LCD
    uint8_t  display_value;     // число, которое LCD рисует рядом с M/S
    uint8_t  slave_count;       // сырое rs485_slave_count_estimate
    uint8_t  node_id;           // сырое rs485_local_node_id
    uint8_t  display_color_id;  // 1=RED, 2=GREEN, 5=CYAN, ...
    uint8_t  display_char;      // 'M', 'S' или 'O'
    uint16_t display_rgb565;    // реальный цвет LCD в RGB565
    uint16_t flags;             // bit0 signal_alive, bit1 sync_ok_visual,
                                 // bit2 color_locked, bit3 display_fallback,
                                // bit4 host_forced,
                                // bit5 role_overlay_enabled,
                                // bit6 role_overlay_active,
                                // bit7 role_persisted, bit8 node_id_conflict
                                // (reserved, zero in fixed-role build),
                                // bit9 multiple_master, bit10 persisted_master
    uint32_t sync_age_ms;       // возраст последнего sync edge; 0xFFFFFFFF если edge не было
    char     text[4];           // готовый префикс LCD: "M03", "S07", "O  "
};
```

Смысл полей:

- `raw_mode` — реальный режим логики sync.
- `display_mode` — режим, который фактически показан на LCD; потеря sync не меняет букву роли.
- `display_value` — постоянный локальный `node_id` и для `MASTER`, и для `SLAVE`.
- `display_color_id` / `display_rgb565` — цвет индикатора на LCD.
- `flags.display_fallback=1` — sync отсутствует; роль/ID при этом остаются `Mxx`/`Sxx`.
- `flags.signal_alive=1` — LCD считает sync "живым".
- `flags.sync_ok_visual=1` — LCD считает sync "хорошим"; после антидребезга цвет становится `GREEN`.
- `flags.color_locked=1` — зелёный уже защёлкнут внутренним state machine LCD.
- `flags.role_overlay_enabled=1` — host разрешил крупный периодический overlay роли.
- `flags.role_overlay_active=1` — на LCD сейчас показан крупный `Mxx`/`Sxx`; в этом состоянии
  `display_rgb565` и `display_color_id` относятся к цвету большого текста.

### 4.1.1. Крупная LCD-индикация роли (`CMD_SET_LCD_ROLE_OVERLAY`, 0x41)

Команда не меняет RS485 sync и не добавляет данных в sync-пакет. Она только управляет локальным
LCD overlay, который отрисовывается из основного цикла с низким приоритетом.

Payload:

- `[0x00]` — запретить overlay и вернуть обычный LCD screen.
- `[0x01]` — разрешить overlay с текущими/дефолтными временами.
- `[enable, period_s, duration_s]` — задать интервал между показами и длительность показа.
  `period_s` и `duration_s` ограничиваются диапазоном `3..5`, дефолт `4/4`.

Формат на LCD:

- `Mxx` — устройство в роли `MASTER`, `xx` = постоянный локальный `node_id`.
- `Sxx` — устройство в роли `SLAVE`, `xx` = локальный `node_id`.
- При ID=0 показывается `M--`/`S--`, а не `M00`/`S00`.
- `O  ` — sync выключен.

Цвет большого текста выбирается случайно из ярких цветов `RED/GREEN/YELLOW/BLUE/CYAN/WHITE`.
EP0 OUT без data stage поддерживает `bRequest=0x41`, младший байт `wValue` = `enable`.
Для задания `period_s/duration_s` используйте bulk OUT или EP0 OUT с data stage.

## 5. Тестовый кадр
Отправляется сразу после `CMD_START_STREAM`.  
Флаги: 0x81 (бит7 TEST + бит0 ADC0).  
`total_samples=8`, фиксированные/диагностические данные.  
Не влияет на фиксацию рабочего размера кадра.

## 6. CRC16 (опционально)
Алгоритм: CRC16-CCITT-FALSE (poly=0x1021, init=0xFFFF, без рефлексии).  
Порядок вычисления: сначала 30 байт заголовка (без поля crc16), затем payload.  
При несоответствии — хост увеличивает `crc_bad` и может сбрасывать поток/запрашивать STOP.

## 7. Инварианты, которые проверяет хост
1. Все рабочие кадры (не TEST) имеют одинаковый `total_samples = exp_samples`.
2. `exp_frame_size` фиксируется по первому рабочему кадру и не меняется.
3. Для каждого `seq` присутствуют либо оба кадра (0x01 и 0x02), либо (во время запуска) временно один; дубликаты запрещены.
4. Нет коротких IN transfers кроме тестового кадра или статусных пакетов <=64B.
5. `crc_bad == 0` при включенном флаге CRC.
6. Без пропусков последовательности (`seq_gaps == 0`) и без откатов.

## 8. Отладочные счётчики прошивки (минимум)
- `produced_seq` — сколько пар сформировано (инкремент после отправки обеих ADC).
- `sent0/sent1` — фактическое кол-во отправленных кадров по каждому ADC.
- `dbg_tx_cplt` — число завершений передачи на уровне USB.
- `dbg_partial_frame_abort` — игнорированных кадров из-за несоответствия размера до фиксации.
- `dbg_size_mismatch` — кадров с неверной длиной (если включено).
- `dma_done0/dma_done1` — завершения DMA.
- `frame_wr_seq` — индекс производственного кольца.

## 8.1. CMD_GET_TEMP (0x31) — Получить температуру кристалла
Читает встроенный температурный датчик STM32H723.

**Request (OUT)**: 1 байт `0x31` (no payload)
**Response (IN)**: 4 байта
- Byte 0: `0x80` (RSP_ACK)
- Byte 1: `0x31` (echo command)
- Bytes 2-3: температура в °C (int16_t, LE)

**Пример**: ответ `[0x80, 0x31, 0x1C, 0x00]` = `+28°C`.

**Заметки**:
- Диапазон: -40°C до +85°C
- Точность: ±5°C (встроенная калибровка датчика)
- Разрешение: 0.5°C
- Время отклика датчика: ~1 ms
- Команда может быть отправлена в любой момент (в режиме потока или ожидания)

## 8.2. CMD_GET_VERSION (0x32) — Получить версию прошивки
Возвращает версию встроенного ПО в формате `MAJOR.MINOR.PATCH`.

**Request (OUT)**: 1 байт `0x32` (no payload)
**Response (IN)**: 6 байт
- Byte 0: `0x80` (RSP_ACK)
- Byte 1: `0x32` (echo command)
- Byte 2: major версия (u8)
- Byte 3: minor версия (u8)
- Byte 4: patch версия (u8)
- Byte 5: build число (u8, зарезервировано, обычно 0)

**Пример**: ответ `[0x80, 0x32, 0x01, 0x02, 0x03, 0x00]` = версия `1.2.3`.

**Заметки**:
- Семантическое управление версионированием (semantic versioning)
- Build число — зарезервировано для будущего использования
- Команда не имеет побочных эффектов и может быть отправлена в любой момент
- Полезна для проверки совместимости хоста и прошивки

## 9. Типичные проблемы и их сигнатуры
| Симптом (хост)                        | Возможная причина прошивки                      |
|--------------------------------------|-------------------------------------------------|
| Только тестовый кадр, далее тишина   | Не стартует DMA / не фиксируется размер         |
| `magic_bad` растёт                   | Перезапись буфера до полной готовности / мусор  |
| `transfer_len_min < transfer_len_max`| Смешаны разные `total_samples`                   |
| `gaps` > 0 при `dup_seq` растущем    | Повторная отправка завершённых seq              |
| Нет статусного ответа                | Статус шлётся на другой endpoint или не формируется |

## 10. Примечания по ROI
CMD_SET_ROI_US: параметр — номер стартового семпла (0..N-1). Прошивка использует длину 200
и сдвигает окно ROI на указанный старт. Если старт выходит за пределы, он ограничивается
в диапазоне 0..(samples-200). Это относится к режимам LOSSLESS_ROI и AVG_ROI.

## 10.1. Единственная скорость DC-компенсации

В прошивке работает один процесс и одна таблица коэффициентов `[channel][parity][sample]`.
RPI задаёт только `settle_ms`; значение действует на каждом новом raw ADC-кадре до следующей
команды и не зависит от режима USB-потока.

`CMD_SET_DC_SPEED (0x1F)` имеет строго один payload:

```c
struct DcSpeedSet {
    uint32_t settle_ms; /* LE; 0=off, 1=fastest, 1000=1 second */
};
```

Полный Bulk OUT пакет равен пяти байтам: `1F ss ss ss ss`. Пакет другой длины или значение
выше `86400000` отвергается. При `settle_ms=0` обучение выключено, но накопленная коррекция
продолжает применяться. При reset скорость становится равной нулю, поэтому RPI явно отправляет
нужное значение при startup/reconnect. В STM32 нет режимов WORK/DETECT/BOOT_FAST, таймеров
acquisition/detection, pre/post-stage и авто-заморозки по амплитуде.

`settle_ms=1` — максимально быстро; `settle_ms=1000` — 1 секунда.
Чем больше ненулевое значение, тем медленнее адаптация.
И модуль, и знак шага рассчитываются отдельно для каждой из 200 точек ROI по её текущему
отклонению. DC применяется ровно
один раз: до усреднения в AVG_ROI или к копии ROI перед отправкой в LOSSLESS_ROI.

В firmware v1.26 коррекция адаптивна для каждой точки:
`corr[i] = abs(error[i]) * 8 * dt_ms / settle_ms`, с ограничением до границы deadband. Знак определяется отдельно
по стороне от virtual zero. Q16-остаток также хранится отдельно для каждой точки, поэтому
малый рассчитанный шаг не теряется. Коэффициент 8 даёт экспоненциальное приближение: максимальная
ошибка 32768 LSB входит в deadband 16 LSB примерно за `0.953 * settle_ms`, а ошибка 1000 LSB —
примерно за `0.518 * settle_ms`. Для `settle_ms=1000` и `dt=10 ms` начальный шаг равен примерно
2620 LSB при максимальном отклонении и 79 LSB при отклонении 1000.
USB START/STOP, повторный START и перезапуск ADC не сбрасывают полученную от RPI скорость или
прошедшее время адаптации. При остановленном USB-потоке фоновая адаптация продолжает работать.

`CMD_GET_DC_CONFIG (0x3A)` рекомендуется читать через EP0 vendor IN. Ответ:

```c
struct DcConfigStatusV2 {
    char     sig[4];       /* "DCCF" */
    uint8_t  version;      /* 2 */
    uint8_t  enabled;      /* settle_ms != 0 */
    uint16_t flags;        /* bit0: coefficients dirty */
    uint32_t settle_ms;
    uint32_t set_at_ms;    /* HAL_GetTick() последней принятой команды */
    uint32_t adapt_updates;
    uint32_t reserved[5];  /* zero; полный размер 40 байт */
};
```

Старые команды `CMD_SET_DC_ADAPT (0x1B)` и `CMD_CALIB_DC_FAST (0x1E)` не
поддерживаются. Старые много-параметрические payload для opcode `0x1F` также
отвергаются, поскольку их длина не равна четырём байтам.

## 11. Roadmap (расширения)
- Динамическая смена размера кадра через новую команду (например 0x31) с подтверждением.
- Включение CRC по отдельной команде (0x32) + бит флага.
- Введение зон (zone_count >0) для сегментации payload.
- Метка точного времени (timestamp 64‑бит) в версии 2 заголовка.

## 12. Требования к обратной совместимости
Изменение структуры `VendorHdr` требует:
1. Инкрементировать `version`.
2. Не изменять первые 12 байт (magic, version, flags, seq) — хост полагается на них.
3. Добавлять новые поля только в хвост либо через `zone` блоки.

## 13. Минимальный алгоритм хоста (C)
1. Открыть устройство, определить ep_in/ep_out.
2. Поставить очередь IN transfers.
3. Отправить SET_* команды.
4. Отправить START_STREAM.
5. Игнорировать тестовый кадр (flags & 0x80).
6. Первый рабочий кадр фиксирует `exp_frame_size`/`exp_samples`.
7. Собираем пары по (seq, flags).
8. По завершении — STOP_STREAM → прочитать статус.

## 14. Диагностический чеклист при регрессии
1. Есть ли тестовый кадр? Если нет — проблема в пути USB передачи.
2. Растут ли dma_doneX? Если нет — ADC/DMA не стартует.
3. Фиксировался ли cur_samples_per_frame? Если 0 — нет первого полного кадра.
4. Есть ли расхождение sent0 != sent1? Если да — один ADC не даёт буфер.
5. Есть дубликаты seq? Если да — повторная отправка того же буфера.

v1.31 — Исправлено ложное срабатывание watchdog WS2812: устаревший `now_ms` из начала длинной итерации больше не превращается в огромный unsigned timeout, поэтому прошивка не выполняет десятки `HAL_SPI_Abort` в секунду и не мешает Vendor USB/EVT1. TX200 приведён к правилу `tx_request AND streaming` без heartbeat-gating. COM `OPTIC` дополнен счётчиками `usb_frame_age_ms/usb_txcplt/usb_recovery/usb_force_idle/usb_error` и `usb_evt_*`.
v1.30 — Оптическое состояние системного WS2812 теперь меняет только цвет, не отключая независимый TX-breathe. Добавлен 100 ms watchdog SPI3 DMA: потерянный callback завершения больше не может навсегда заморозить системный LED; COM `OPTIC` сообщает `ws_busy/ws_frames/ws_recoveries`.
v1.29 — Восстановлена локальная системная WS2812-индикация optic. Зафиксирован единый сигнал `optic_active = PD0 || hold_after_last_high`: HIGH немедленно включает и повторно запускает hold, LOW таймер не запускает и не продлевает. Этот же удержанный сигнал используется системным LED, LCD, USB, RS485 и картой группы; его изменения публикуются как `EVT1 SENSOR_MAP` и полный совместимый `STAT v5`. Локальный optic получил высший приоритет и постоянную яркость на системном LED, чтобы error-state и TX-breathe не скрывали срабатывание. Исправлено legacy-смещение ID в 136-байтовом статусе.
v1.28 — Роль и `node_id` стали независимыми локальными настройками каждой платы и сохраняются во Flash. Отключены автоматическая нумерация, compact-assignment и сетевое переназначение роли. `Mxx/Sxx` показывают один постоянный ID; `STAT/LCDS/EVT1/RID1` сообщают сохранённую роль, конфликт ID и несколько master.
v1.27 — Зафиксированы единицы `SET_DC_SPEED`: raw `uint32` задан в миллисекундах (`0` — off, `1` — максимально быстро, `1000` — 1 с). В UART-команду `DC` добавлен readback фактически принятого `settle_ms`.
v1.26 — Общий постоянный DC-шаг заменён адаптивной коррекцией каждой точки пропорционально её текущему отклонению. Максимальная ошибка входит в deadband примерно за указанное RPI `settle_ms`; формат `SET_DC_SPEED` не изменён.
v1.25 — Роли назначаются только RPI и восстанавливаются из Flash без UID-голосования; смена роли больше не трогает TX200, rate override и ADC/DMA sequence. `SET_DC_SPEED=1000` откалиброван как 32768 LSB/s; DC продолжает работать при USB STOP/ADC restart. Для S03 добавлено локальное восстановление hard-stall Bulk IN и идемпотентная обработка повторных START/rate-команд.
v1.24 — DC сведен к одной непрерывной адаптации и одному параметру `SET_DC_SPEED settle_ms`; удалены режимы, таймеры, pre/post, amplitude gate и legacy DC-команды.
v1.23 — Устранён повторный выброс DC после быстрой компенсации: mode-only v2 config больше не меняет pre/post stage, при явной смене stage очищаются только незавершённые AVG-группы, после ADC restart заново сопоставляются even/odd банки, а выход из BOOT_FAST ставит один save актуальной общей таблицы во Flash.
v1.22 — DC хранится одной общей таблицей `[channel][parity][200]` для pre/post; стадии взаимоисключающие и не очищают коэффициенты при переключении. Автосохранение DC отключено, долговременная запись выполняется явной `SAVE_DC_TO_FLASH (0x2B)`.
v1.21 — Добавлено сохраняемое timestamped-назначение одного sensor-slave с автоматическим освобождением старого выбранного slave. `STAT` и `RID1` показывают назначение и sensor status. Identity-scan master теперь реплицирует всем устройствам полный каталог номер/IP; master хранится в отдельной строке `32`, slave — в `1..31`.
v1.20 — Сетевое назначение RS485 master теперь содержит `u64 Unix ms`, распространяется по UID96, сохраняется всеми устройствами и разрешает конфликт в пользу более нового назначения. Slave-нумерация стала последовательной, UID-адресованной и подтверждаемой; при отсутствии назначения сохранено прежнее UID-голосование.
v1.19 — Восстановлена стабильная синхронизация TX200; устранено асинхронное вмешательство фонового TX service. Внешний host-контракт остаётся `SET_TX_ENABLE 0/1` плюс обязательный readback.
v1.18 — Временный ошибочный вариант управления TX200, отменённый в v1.19. Временно отключена зависимость TX от streaming/SOF/heartbeat/STOP.
v1.17 — `SET_TX_ENABLE`/`TX200` стал persistent request: только явный `0/1` меняет запрос. `STOP_STREAM` гасит физический TX без стирания request, а `START_STREAM` автоматически восстанавливает сохранённое состояние. Приём `0x33` теперь отражается в `last_cmd_received`.
v1.16 — Исправлен самопроизвольный сброс 200 Hz TX: `HOST_RX_CLEAR` очищает только heartbeat и больше не меняет `tx_req`. Зафиксирован порядок host-команд `CLEAR -> STOP -> config -> START -> SET_TX_ENABLE`; `vendor_stream_read.py --tx-enable` перенесён после START.
v1.13 — `STAT v5` экспортирует существующий RS485 `master_status0 bit5` на slave-host через `flags_runtime bit0x0080`, без увеличения размера `STAT` выше 136 байт.
v1.15 — `SET_TX_ENABLE` снова является главным host-request для 200 Hz marker/TX: `START_STREAM` и `HOST_RX_ACK` не включают TX поверх команды host. Fail-safe гасит только физический выход при отсутствии host USB/SOF и потока.
v1.14 — 200 Hz marker/TX получил host-stream fail-safe: TX выключен по умолчанию, включается на `START_STREAM` и гаснет на `STOP_STREAM`/`HOST_RX_CLEAR`/устаревшем `HOST_RX_ACK`; optic-gate на него не влияет.
v1.12 — 200 Hz marker/TX восстановлен как постоянно включенный по умолчанию и больше не входит в optic-gate; `TX200`/`SET_TX_ENABLE` оставлены для будущего управления другим датчиком.
v1.11 — Optic-gate для внешних световых эффектов: внешняя WS2812-лента остается выключенной, пока нет локального или свежего принятого по RS485 `optic_active`; оптический 38 kHz carrier остается независимым, чтобы приемник мог сработать.
v1.10 — Role-based optic indication: master меняет синий на зеленый при локальном `optic_active=1`; slave меняет белый на желтый при своем локальном `optic_active=1`, а по свежему `master_status0 bit5` без локального срабатывания меняет белый на магента/фиолетовый.
